# Pintos 파일 시스템 개념 요약

## 1. 디스크와 sector

디스크는 파일, 디렉토리, inode를 모른다.

```text
disk = sector들의 배열
sector = 디스크가 읽고 쓰는 기본 단위
```

Pintos에서 파일 시스템은 sector 단위로 `read/write`를 요청한다.
어떤 sector가 inode인지, 디렉토리인지, 파일 데이터인지는 **파일 시스템 코드가 정한 해석 규칙**이다.

---

## 2. sector와 cluster

```text
sector
= 디스크 I/O 기본 단위

cluster
= 파일 시스템이 정한 할당 단위
= sector 여러 개를 논리적으로 묶은 것
```

cluster를 크게 잡으면:

```text
장점:
  큰 파일이 더 적은 cluster로 표현됨
  FAT chain 길이가 짧아짐
  metadata 접근이 줄어듦

단점:
  작은 파일에서 내부 단편화 증가
```

cluster를 작게 잡으면:

```text
장점:
  작은 파일의 공간 낭비 감소

단점:
  큰 파일은 많은 cluster를 필요로 함
  FAT chain이 길어짐
```

Pintos Project 4의 단순 FAT에서는 보통:

```text
1 cluster = 1 sector
```

로 보면 된다.

---

## 3. 파일 시스템의 기본 역할

파일 시스템은 sector 배열 위에 다음 의미를 부여한다.

```text
어디가 metadata 영역인가
어디가 free space인가
root directory는 어디인가
파일 이름은 어떤 inode를 가리키는가
inode는 실제 file data를 어디서 찾는가
파일 크기는 얼마인가
```

즉 파일 시스템은 디스크 위의 **자료구조 포맷**이다.

---

## 4. inode

inode는 파일 시스템이 정의한 **파일/디렉토리 객체의 메타데이터**다.

```text
inode
= 파일 하나 또는 디렉토리 하나를 대표하는 메타데이터 객체
```

디스크 하드웨어 개념이 아니다.
파일 시스템 구현이 정의하는 논리적 객체다.

---

## 5. on-disk inode

```text
on-disk inode
= 디스크에 저장되는 inode 메타데이터
= 영속 데이터
```

Pintos 기본 구조에서는 inode 하나가 disk sector 하나를 차지한다.

중요한 점:

```text
on-disk inode는 파일 데이터 앞에 붙는 header가 아니다.
on-disk inode sector와 file data sector는 분리되어 있다.
```

개념적으로:

```text
inode sector N:
  length
  start sector 또는 first cluster
  file/directory type
  magic
  기타 metadata

data sector들:
  실제 파일 내용
```

---

## 6. in-memory inode

```text
in-memory inode
= 커널 메모리에 올라온 inode 관리 객체
= 실행 중에만 존재
```

주로 가진다.

```text
on-disk inode가 있는 sector 번호
open_cnt
removed
deny_write_cnt
lock
cache 관련 정보
```

역할:

```text
open/close/remove 관리
write deny 관리
file length 확인
file offset -> disk sector 변환
file growth 관리
```

---

## 7. struct file

```text
struct file
= open()으로 열린 파일 핸들
```

파일 자체가 아니라 **열린 객체 하나**다.

가지는 정보:

```text
inode pointer
현재 offset / pos
이 open handle의 deny_write 여부
```

같은 inode를 여러 번 열 수 있다.

```text
fd 3 -> struct file A -> inode X
fd 4 -> struct file B -> inode X
```

이때 `file A`, `file B`는 같은 실제 파일을 가리키지만 offset은 다를 수 있다.

---

## 8. directory

디렉토리는 특수한 파일이다.

```text
directory
= 이름 -> inode sector 매핑을 데이터로 가진 파일
```

디렉토리도 inode를 가진다.
다만 그 파일 데이터의 형식이 일반 byte stream이 아니라 directory entry 배열이다.

```text
directory data:

"name1" -> inode sector 10
"name2" -> inode sector 25
"name3" -> inode sector 40
```

`struct dir`은 열린 디렉토리 핸들이다.

```text
struct dir
  inode pointer
  readdir position
```

---

## 9. path resolution

경로 탐색은 디렉토리 파일을 반복해서 읽는 과정이다.

```text
/a/b/c.txt
```

처리 흐름:

```text
root directory inode에서 시작
"a" entry 검색
a의 inode 열기
a가 directory인지 확인
"b" entry 검색
b의 inode 열기
"c.txt" entry 검색
최종 inode 획득
```

즉 파일 이름은 직접 파일 데이터를 가리키지 않는다.
항상 directory entry를 통해 inode를 찾는다.

---

## 10. Pintos 기본 파일 배치

기본 Pintos는 파일 데이터를 하나의 연속된 구간에 저장한다.

```text
inode:
  length = 파일 크기
  start = 첫 data sector

file data:
  start
  start + 1
  start + 2
  ...
```

이 방식은 단순하지만 문제가 있다.

```text
파일 크기 고정
파일 확장 어려움
연속된 빈 공간이 없으면 큰 파일 생성 실패
외부 단편화 문제
```

---

## 11. FAT 방식

FAT는 파일 데이터 cluster들의 연결 관계를 전역 테이블에 저장한다.

```text
FAT[현재 cluster] = 다음 cluster
```

예:

```text
inode:
  first_cluster = 7
  length = 2000

FAT:
  FAT[7]  = 20
  FAT[20] = 31
  FAT[31] = EOF
```

파일 데이터는:

```text
cluster 7 -> cluster 20 -> cluster 31 -> EOF
```

에 저장된다.

---

## 12. FAT의 의미

FAT는 inode들의 연결이 아니다.

```text
파일 하나
= inode 하나
+ FAT chain 하나
+ data cluster 여러 개
```

FAT chain은 data cluster들의 연결이다.

```text
inode
  first_cluster = 7

FAT chain
  7 -> 20 -> 31 -> EOF
```

---

## 13. FAT의 장단점

장점:

```text
파일 데이터가 연속될 필요 없음
빈 cluster 하나만 있어도 파일 확장 가능
외부 단편화 문제 감소
구현 단순
```

단점:

```text
큰 파일의 중간 위치 접근 시 chain을 따라가야 함
랜덤 접근에 약함
연속 cluster도 FAT entry를 계속 저장해야 함
대용량 파일 시스템에는 비효율적
```

그래서 실제 현대 파일 시스템은 extent, B-tree, inode indexing 등을 쓰기도 한다.

---

## 14. direct / indirect / double indirect

Unix 계열 파일 시스템에서는 inode 안에 block pointer를 직접 넣는 방식도 쓴다.

```text
direct block pointer
  작은 파일을 바로 가리킴

indirect block pointer
  block pointer 배열을 가리킴

double indirect block pointer
  indirect block들의 배열을 가리킴
```

하지만 Pintos Project 4에서는 이 방식이 아니라 **FAT 방식**을 사용한다.

---

## 15. buffer cache

buffer cache는 disk sector를 메모리에 캐싱한다.

```text
disk sector read
  cache hit  -> 메모리에서 바로 읽음
  cache miss -> disk에서 읽고 cache에 저장

disk sector write
  cache에 쓰고 dirty 표시
  나중에 disk에 write-back
```

중요한 상태:

```text
valid
dirty
accessed
sector number
data buffer
lock
```

cache가 꽉 차면 eviction이 필요하다.

```text
eviction
= 어떤 cache block을 내보낼지 선택하는 과정
```

dirty block은 버리기 전에 disk에 반영해야 한다.

---

## 16. 핵심 책임 분리

```text
disk driver
  sector read/write만 수행
  파일 시스템 의미를 모름

file system
  sector 배열에 의미를 부여
  inode, directory, FAT, free map 관리

inode
  파일/디렉토리 하나의 metadata

file
  열린 일반 파일 handle

dir
  열린 디렉토리 handle

FAT
  data cluster들의 연결 관계 관리

buffer cache
  disk I/O를 줄이기 위한 sector cache
```

## 최종 모델

```text
disk
  sector 배열

file system metadata
  superblock / boot sector
  free map 또는 FAT
  root directory 위치

directory
  name -> inode sector

inode sector
  file length
  first data location
  type
  metadata

```

# 보완 정리: Pintos 모델과 실제 파일 시스템의 차이

## 1. Pintos는 학습용 단순 모델

Pintos에서는 개념적으로:

```text
inode 하나 = disk sector 하나
```

처럼 다룬다.

이 구조는 이해하기 쉽지만 실제 파일 시스템 기준으로는 비효율적이다.

```text
문제:
  inode 하나가 sector 하나를 독점
  metadata 공간 낭비 발생
  많은 파일을 다룰 때 비효율 증가
```

---

## 2. 실제 파일 시스템은 inode를 더 조밀하게 관리

실제 Unix 계열 파일 시스템은 보통 inode들을 별도 영역에 모아둔다.

```text
inode table
  inode
  inode
  inode
  ...
```

즉 실제로는:

```text
inode 하나가 sector 하나를 통째로 차지
```

하기보다는:

```text
여러 inode를 block/table 안에 조밀하게 저장
```

하는 경우가 많다.

---

## 3. Pintos의 FAT도 실제 FAT의 단순화 버전

실제 FAT에는 여러 표준이 있다.

```text
FAT12
FAT16
FAT32
exFAT
```

하지만 Pintos의 FAT는 특정 표준 호환 구현이 아니다.

```text
Pintos FAT
= FAT의 핵심 아이디어만 가져온 단순화된 구조
```

핵심은 다음뿐이다.

```text
FAT[현재 cluster] = 다음 cluster
EOF = chain 끝
free = 비어 있는 cluster
```

---

## 4. 실제 파일 시스템은 더 복잡하다

Pintos에서 다루는 주요 모델:

```text
기본 Pintos:
  inode + 연속 sector

Project 4 Pintos:
  inode + FAT chain
```

실제 파일 시스템은 여기에 더해 다양한 구조를 사용한다.

```text
direct / indirect / double indirect
extent
B-tree / B+tree
journaling
copy-on-write
checksum
delayed allocation
```

세부 구현을 지금 알 필요는 없고, **Pintos보다 훨씬 복잡한 최적화가 들어간다**는 정도만 알면 된다.

---

## 5. 핵심 비교

```text
Pintos 기본:
  단순함
  inode sector 사용
  연속 sector 기반
  외부 단편화에 약함

Pintos FAT:
  FAT[cluster] = next cluster
  불연속 저장 가능
  구현 단순
  긴 파일 랜덤 접근은 비효율적

실제 Unix 계열:
  inode table 사용
  inode를 조밀하게 관리
  block pointer 또는 extent 사용

현대 파일 시스템:
  extent + tree 구조 중심
  대용량 파일과 많은 metadata를 효율적으로 관리
```

---

## 최종 요약

```text
Pintos 파일 시스템은 실제 파일 시스템의 완성형 구조가 아니라,
inode, directory, FAT, buffer cache 같은 핵심 개념을 단순한 sector 모델 위에서 이해하기 위한 교육용 구현이다.
```

Pintos 구조를 실제 파일 시스템의 표준 형태로 보면 안 되고, **실제 파일 시스템은 inode 관리, block 배치, metadata 검색, crash 복구 등을 훨씬 더 정교하게 처리한다**고 보면 된다.

## 1. 파일시스템 요구사항 요약

Pintos Project 4 요구사항은 크게 이 정도입니다.

```text
1. FAT 기반 file growth
   - 기본 single extent 제거
   - FAT chain으로 불연속 cluster 연결
   - EOF 이후 write 시 파일 확장
   - seek 자체는 확장 아님

2. subdirectory
   - 계층형 경로 지원
   - absolute/relative path 지원
   - ".", ".." 지원
   - process별 current working directory 유지

3. directory syscall
   - chdir
   - mkdir
   - readdir
   - isdir
   - inumber

4. symlink
   - target path 문자열을 담는 특수 inode 구현

5. synchronization
   - 원칙상 coarse global FS lock이 아니라 finer-grained lock 필요

6. buffer cache
   - 64 sector 이하 cache
   - clock 이상 eviction
   - write-behind
   - read-ahead
```

공식 요구사항상 file growth는 FAT로 구현해야 하고, multi-level indexing은 쓰면 안 됩니다. 또한 inode 하나는 disk sector 하나에 저장된다고 전제합니다. ([Casys KAIST][1])
subdirectory는 계층형 namespace, per-process cwd, `.`, `..`, directory open/remove, `chdir/mkdir/readdir/isdir/inumber`, symlink를 요구합니다. ([Casys KAIST][2])
buffer cache는 64 sector 제한, clock 이상 replacement, write-behind, read-ahead를 요구합니다. ([Casys KAIST][3])
동기화 요구사항은 원칙적으로 독립 cache block, 독립 directory, 비확장 write/read 등이 병렬 가능해야 한다는 것입니다. ([Casys KAIST][4])

## 3. FAT 구현

FAT는 전역 배열입니다.

```c
struct fat_fs {
    struct fat_boot bs;
    unsigned int *fat;
    unsigned int fat_length;
    disk_sector_t data_start;
    cluster_t last_clst;
    struct lock write_lock;
};
```

이 프로젝트는 FAT boot 정보를 읽고, FAT table을 메모리에 올린 뒤, 종료 시 다시 disk에 씁니다. `fat_fs`에는 FAT 배열, cluster 개수, data area 시작 sector, 마지막 cluster, write lock이 들어갑니다. ([GitHub][7])

핵심 동작:

```c
cluster_t fat_create_chain(cluster_t clst) {
    find free FAT entry;
    fat[new_clst] = EOChain;
    if (clst != 0)
        fat[clst] = new_clst;
    return new_clst;
}

void fat_remove_chain(cluster_t clst, cluster_t prev) {
    if (prev != 0)
        fat[prev] = EOChain;

    while (clst valid) {
        next = fat[clst];
        fat[clst] = 0;
        clst = next;
    }
}

cluster_t fat_get(cluster_t clst) {
    return fat[clst];
}

disk_sector_t cluster_to_sector(cluster_t clst) {
    return data_start + (clst - 1) * sectors_per_cluster;
}
```

실제 코드도 free entry를 찾아 `EOChain`으로 만들고, 기존 cluster 뒤에 붙입니다. 제거할 때는 chain을 따라가며 FAT entry를 `0`으로 되돌립니다. ([GitHub][7])

## 4. inode 구조

on-disk inode는 FAT 첫 cluster와 타입을 가집니다.

```c
struct inode_disk {
    cluster_t start;     // first data cluster
    off_t length;        // file size
    unsigned magic;
    uint32_t type;       // file / dir / symlink
    uint32_t unused[124];
};
```

in-memory inode는 runtime 상태를 가집니다.

```c
struct inode {
    struct list_elem elem;
    disk_sector_t sector;
    int open_cnt;
    bool removed;
    int deny_write_cnt;
    struct inode_disk data;
};
```

`inode_type`은 `INODE_FILE`, `INODE_DIR`, `INODE_SYMLINK`로 나뉩니다. ([GitHub][8])
즉 이 프로젝트는 inode 하나로 일반 파일, 디렉토리, symlink를 모두 표현합니다.

---

## 5. byte offset → sector 변환

FAT 적용 전에는 `start + offset / sector_size`였지만, EFILESYS에서는 FAT chain을 따라갑니다.

```c
static disk_sector_t byte_to_sector(const struct inode *inode, off_t pos) {
    if (pos >= inode->data.length)
        return -1;

    clst = inode->data.start;
    skip = pos / DISK_SECTOR_SIZE;

    while (skip-- > 0)
        clst = fat_get(clst);

    return cluster_to_sector(clst);
}
```

코드상 `byte_to_sector()`는 `inode->data.start`에서 시작해 `pos / DISK_SECTOR_SIZE`만큼 FAT chain을 따라간 뒤 sector로 변환합니다. ([GitHub][9])

---

## 6. file growth 구현

EOF 이후 write가 들어오면 `inode_extend()`로 FAT chain을 늘립니다.

```c
if (size > 0 && offset + size > inode->data.length) {
    if (!inode_extend(inode, offset + size))
        return 0;
}
```

`inode_extend()`는 필요한 sector 수를 계산하고, 부족한 만큼 `fat_create_chain()`으로 새 cluster를 붙인 뒤 zero-fill하고 inode length를 갱신합니다. ([GitHub][9])

축약하면:

```c
static bool inode_extend(struct inode *inode, off_t length) {
    old = bytes_to_sectors(inode->data.length);
    new = bytes_to_sectors(length);

    for (i = old; i < new; i++) {
        new_clst = fat_create_chain(last_clst);
        zero_cluster(new_clst);
    }

    inode->data.length = length;
    disk_write(filesys_disk, inode->sector, &inode->data);
}
```

## 7. directory 구현

directory는 inode를 backing store로 쓰는 wrapper입니다.

```c
struct dir {
    struct inode *inode;
    off_t pos;
};

struct dir_entry {
    disk_sector_t inode_sector;
    char name[NAME_MAX + 1];
    bool in_use;
};
```

`dir_create_with_parent()`는 directory inode를 만들고, 바로 `"."`, `".."` entry를 추가합니다. ([GitHub][10])

```c
bool dir_create_with_parent(sector, parent_sector) {
    inode_create_typed(sector, 0, INODE_DIR);
    dir_add(dir, ".", sector);
    dir_add(dir, "..", parent_sector);
}
```

`dir_add()`는 빈 `dir_entry` slot을 찾고, 없으면 EOF에 씁니다. directory도 file growth 대상이므로 directory entry가 늘어나면 inode가 확장됩니다. ([GitHub][10])

---

## 8. path resolution

`filesys.c`가 absolute/relative path, cwd, symlink follow를 처리합니다.

핵심 흐름:

```c
resolve_path(path):
    시작 dir = path[0] == '/' ? root : cwd
    component를 하나씩 분리
    dir_lookup()
    중간 component는 directory여야 함
    symlink면 target path로 재귀 resolve
```

코드에는 `resolve_path_from()`, `resolve_parent()`, `dir_for_path_start()`가 있고, `/`로 시작하면 root, 아니면 현재 thread의 `cwd`에서 시작합니다. symlink는 depth 제한 `SYMLINK_MAX_DEPTH = 8`로 재귀 resolve합니다. ([GitHub][11])

## 9. create / mkdir / symlink

일반 파일 생성:

```c
resolve_parent(name, &dir, basename);
allocate_inode_sector(&inode_sector);
inode_create_typed(inode_sector, initial_size, INODE_FILE);
dir_add(dir, basename, inode_sector);
```

directory 생성:

```c
resolve_parent(name, &dir, basename);
allocate_inode_sector(&inode_sector);
dir_create_with_parent(inode_sector, parent_inode_sector);
dir_add(dir, basename, inode_sector);
```

symlink 생성:

```c
inode_create_typed(inode_sector, target_len, INODE_SYMLINK);
inode_write_at(inode, target, target_len, 0);
dir_add(dir, basename, inode_sector);
```

이 흐름은 `filesys_create()`, `filesys_mkdir()`, `filesys_symlink()`에 들어 있습니다. ([GitHub][11])

## 10. file 객체가 directory도 감쌈

`struct file`에 `struct dir *dir`을 추가해서, fd 하나로 일반 파일과 디렉토리를 모두 표현합니다.

```c
struct file {
    struct inode *inode;
    struct dir *dir;   // directory면 non-null
    off_t pos;
    bool deny_write;
};
```

`file_open()`에서 inode가 directory면 `dir_open()`으로 감싸고, 일반 파일이면 그대로 inode를 들고 갑니다. `file_read/write()`는 directory에 대해 실패시키고, `file_readdir()`은 `dir_readdir()`로 위임합니다. ([GitHub][12])

## 11. syscall 연결

Project 4 syscall은 `syscall.c`에서 `filesys_*` 함수로 연결됩니다.

```c
handle_chdir   -> filesys_chdir
handle_mkdir   -> filesys_mkdir
handle_readdir -> file_readdir
handle_isdir   -> file_is_dir
handle_inumber -> inode_get_inumber(file_get_inode(file))
handle_symlink -> filesys_symlink
```

실제 dispatch table에도 `SYS_CHDIR`, `SYS_MKDIR`, `SYS_READDIR`, `SYS_ISDIR`, `SYS_INUMBER`, `SYS_SYMLINK`가 추가되어 있습니다. ([GitHub][13])

## 12. cwd와 fd 관리

`struct thread`에 파일시스템 관련 상태가 추가되어 있습니다.

```c
struct thread {
    struct list file_descriptors;
    struct file *executable;
    struct dir *cwd;
};
```

즉 process별 fd table과 cwd를 thread가 들고 있습니다. ([GitHub][14])

## 13. synchronization 평가

요구사항은 finer-grained synchronization이지만, 이 프로젝트는 syscall handler에서 대부분 `filesys_lock`을 잡습니다.

```c
lock_acquire(&filesys_lock);
entry->return_value = filesys_create(...);
lock_release(&filesys_lock);
```

`create/remove/open/read/write/chdir/mkdir/readdir/symlink` 등 대부분이 global `filesys_lock`으로 보호됩니다. ([GitHub][13])

평가:

```text
correctness 단순화:
  좋음

요구사항의 fine-grained concurrency:
  충분하지 않음
```

## 최종 요약

이 프로젝트의 파일시스템 구현은 다음 구조입니다.

```text
FAT:
  cluster chain으로 file growth 구현

inode:
  start cluster + length + type
  file / dir / symlink 공통 표현

directory:
  dir_entry 배열
  "." / ".." 지원
  directory도 inode 기반 확장 가능

path:
  absolute / relative / cwd / symlink follow 처리

file:
  일반 파일과 directory fd를 하나의 struct file로 통합

syscall:
  chdir, mkdir, readdir, isdir, inumber, symlink 연결

미흡:
  buffer cache 비활성
  synchronization은 global filesys_lock 중심
```

핵심만 보면, **Project 4의 필수 기능인 FAT file growth와 subdirectory/symlink는 구현했고, buffer cache와 fine-grained synchronization은 요구사항 수준까지는 구현되지 않은 상태**입니다.
