## VM과 Swap 개념 이해하기

어제 정리한 page table/pte, spt 역할 부분은 생략하고 나머지 전체적은 흐름 부분

swap in은 “page 내용을 새 physical frame으로 가져오는 작업”
swap out은 “현재 physical frame에 올라와 있는 page 내용을 backing store에 보존하고, 그 frame을 다른 page가 쓸 수 있게 비우는 작업”

### SPT와 Swap

(이쪽 파트는 뇌피셜)

처음 봤을 때, aux나 메타데이터는 왜 따로 저장하지 않는지 궁금했는데,

이러한 메타데이터는 매우 적은 용량이라서 굳이 디스크에 저장하거나 할 필요는 없다.

즉, SPT는 Swap 대상이 아니다. 한 frame의 내용은 4KB인데 반해서,
한 frame을 관리하는데 쓰이는 메타데이터는 그보다 훨씬 작은 양이고,
이걸 저장하는 효율 대비 추가되는 처리량이 더 클 것이다.

### 각 타입 별 Swap 정리

각 함수의 역할은 대충 알겠으니, 이걸 어떻게 타입별로 구현했는지 분석하기.

- 공통
    - swap in 전/후: `vm_do_claim_page()` 에서
        - page, frame, owner thread 등의 메타 정보를 저장하고, frame list에 추가한다.
        - 에러가 난 경우 이러한 자원을 해제하고 실패 처리한다.
    - swap out 전/후: `vm_evict_frame()` 에서
        - 요약: swap out을 하고, SPT entry와 pml4에 비워졌다고 인식하도록 상태를 동기화한다.
        - 기존 page 내용을 먼저 `swap_out()`으로 보존한다.
        - pml4에서 해당 page mapping을 clear 한다. (그래야 MMU 입장에서 빈 상태로 인식함)
        - SPT entry 자체는 유지하고, page와 frame의 연결 정보를 비운다.

- uninit
    - swap in: 생성 시 건네준 init 함수를 호출하고, 각 타입에 맞는 initializer를 호출함.
        - initializer는 각 타입에 맞는 하위 page 구현체를 기본 값으로 초기화하는 역할이다.
        - 인자로 넘긴 init 함수는 aux와 같은 추가 데이터를 받아 정보를 할당받는 역할이다.
    - swap out: 없다. frame 연결이 없으니 비워줄 것도 없다.

- anon
    - swap in:
        - swap disk에 저장된 내용을 새로 전달받은 물리 메모리에 쓴다.
        - swap disk에서 데이터가 저장된 위치는 page metadata에 저장된 `swap_slot`를 사용해 찾는다.
        - 처음 claim되는 경우, page라면 swap disk에서 읽는 것이 아니라 zero page로 준비한다.
    - swap out:
        - swap_table(비트맵)의 `bitmap_scan_and_flip()` 연산을 통해 swap disk의 할당 가능한 공간을 찾는다.
        - 현재 frame의 내용을 해당 swap slot에 저장한다.

- file_backed
    - swap in:
        - SPT에 저장된 파일과 오프셋 정보를 기반으로 새 frame의 내용을 채운다.
    - swap out:
        - dirty page인 경우 원본 파일에 쓰고, 아니면 바로 종료한다.

swap table은 비트맵 기반으로 swap 가능 여부를 효율적으로 표시한다.
frame table은 list에 FIFO 규칙을 지켜서 작성하므로, 가장 오래전에 추가되었던 프레임을 제거하도록 한다.

## mmap 정리

swap 상황, uninit page가 실제로 로드되는 과정, file-backed swap in/out 과정은 일반 file-backed page와 동일하므로 생략한다.

1. mmap 시에는 file을 `file_reopen()`해서 mmap 전용 file handle을 만든다.
    - fd가 닫혀도 mmap은 유지되어야 하므로, 기존 fd와 mmap의 file 수명을 분리하는 것이 좋다.
2. 이후 각 page에는 같은 file과 각자의 offset/read 정보를 저장한다.
    - page마다 필요한 위치만 다르므로 file은 공유하고, offset 같은 상태만 page별로 들고 있으면 된다.
    - file은 ref count 기반으로 관리하면 여러 page가 같은 file을 보더라도 close 시점을 다루기 쉽다.
3. munmap과 process exit(SPT kill)은 destroy를 호출하여 page를 정리한다.
    - munmap은 mmap 범위의 page를 제거하고, process exit은 SPT 전체를 제거한다.
    - 둘 다 공통적으로 page destroy를 호출하므로, dirty write-back과 file 정리를 destroy에서 수행한다.

## Stack Growth 정리

1. stack page도 결국 SPT에 등록된다.
    - 다만 필요해질 때 anonymous page로 추가한다.
    - 가능한 스택 공간을 미리 다 spt에 entry로 관리해놓지 않는다.
2. 유효한 접근인지 확인하는 휴리스틱으로 평가한다.
    - fault 주소가 user stack 범위 안에 있고, 현재 user `rsp` 근처일 때만 stack 접근으로 본다.
    - x86-64 `push`는 `rsp`보다 8 bytes 아래에서 fault가 날 수 있으므로 이 경우도 허용한다.
3. stack growth로 판단되면 해당 주소의 page를 만들고 바로 claim한다.
    - user mode fault는 fault frame의 `rsp`를 보고,
    - kernel에서 user buffer 접근 중 난 fault는 syscall 진입 때 저장한 user `rsp`를 기준으로 판단한다.

## interrupt/exception과 page fault

추가적으로 다루자면 interrupt/exception 종류 정도만 보면 될 듯하다.

CPU가 현재 실행 흐름을 멈추고 handler로 이동하는 경우는 크게 interrupt와 exception으로 나눠 볼 수 있다.

1. interrupt
    - timer, device I/O처럼 외부 장치가 비동기적으로 발생시킨다.
    - 현재 실행 중인 명령어 자체와 직접 관련이 없고, 처리 후 다음 흐름으로 돌아간다.
2. exception
    - 현재 실행 중인 명령어 때문에 동기적으로 발생한다.
    - exception은 다시 fault, trap, abort 정도로 나눌 수 있다.
    - fault는 명령어가 완료되기 전에 발생하며, handler가 해결하면 같은 명령어를 다시 실행할 수 있다.
    - trap은 명령어가 끝난 뒤 보고되므로 보통 다음 명령어부터 이어진다.
    - abort는 복구하기 어려운 심각한 오류에 가깝다.

page fault의 경우에는?
- page fault는 이름을 보면 당연하게도... fault에 속한다.
- 메모리 접근 명령어 실행 중 page table 권한이나 present bit 문제를 CPU/MMU가 감지해서 발생한다.
- VM에서는 이 특성을 이용해 lazy load, stack growth, swap in을 처리한 뒤 같은 명령어를 다시 실행하게 만든다.
