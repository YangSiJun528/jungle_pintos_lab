            - 동기화: 여러 실행 흐름이 있어도 동시성 문제가 발생하지 않게 하는 것
            - 임계 영역 문제 해결을 위한 3가지 조건: 상호 배제, 진행(진행되어야 함), 유한 대기(bounded waiting)
            - 락이 가능한 이유: CPU가 원자적 read-modify-write 명령어를 지원하기 때문.
            - 스핀락: 락을 얻을 때까지 반복 확인하며 대기. 다른 락 함수에서 임계 영역 보호에 내부적으로 사용됨.
            - 뮤텍스: 락을 얻지 못하면 대기하며 CPU를 양보한다.
                - mutex 대기자는 unlock 이후 OS/runtime이 깨운다. 조건 자체를 기다려야 하면 condition variable을 함께 쓰며, 이때는
                  signal/broadcast로 조건 대기자를 깨운다.
            - 세마포: 정해진 개수만큼 프로세스/스레드가 임계 영역 또는 작업을 진행하게 함. wait/post로 자원 수나 이벤트 발생 횟수를 제어함.
                - 보장하는 것: A 이벤트가 N번 발생해야 B 작업이 N번 진행 가능하다.
                - 실제론 잘 안쓰고, 조건 대기가 없으면서 단순히 동시에 N개까지만 실행을 허용하는 제어가 필요한 경우에 씀.
            - condition variable: 조건 대기를 식별하는 동기화 객체.
                - 조건 자체는 저장/검사하지 않고, wait/signal/broadcast로 대기와 깨움을 처리한다.
                - cv에 대한 대기자 관리는 런타임/OS가 담당한다. (주로 대기 큐로 관리되지만, 깨움 순서나 다음 실행 순서가 FIFO로 보장되지는 않음.)
                - mutex와 자동으로 묶이지는 않으므로, 사용자가 공유 상태를 보호하는 mutex를 직접 함께 넘겨야 한다.
                - wait(cv, mutex): 현재 스레드를 cv에 대한 조건 대기 상태로 만들고 mutex를 놓은 뒤 잠든다. 깨어나면 wait 반환 전에 mutex를 다시 획득한다.
                    - 대기 상태는 큐에 들어가서 대기 상태로 관리된다.
                - signal/broadcast: cv에 대해 대기 중인 스레드 하나 또는 전체를 깨운다.
                - wait 반환 후 조건은 사용자 코드가 while로 다시 확인한다.
            - monitor: 공유 상태를 접근 함수로만 제어하게 만든 동기화 구조.
                - 내부적으로 mutex로 공유 상태 접근을 보호하고, 필요하면 condition variable로 조건 대기를 처리한다.
                - mutex + condition variable 패턴을 더 안전하고 쓰기 쉽게 추상화한 것.

### 코드 분석 중 궁금한거 찾아서 정리

- **세마포어 사용 패턴 중 - Signaling(신호 전달)**
    - Initialization barrier라고 부르기도 함.
    - 한 스레드가 특정 지점에 도달했음을 다른 스레드에 알리는 1회성 신호로써 사용.
    - `void thread_start (void)`에서 사용함.
    - https://w3.cs.jmu.edu/kirkpams/OpenCSF/Books/csf/html/SynchDesign.html
- **특정 코드에서 인터럽트 비활성화 하는 이유**
    - Pintos(+그리고 현대 리눅스)는 Preemptible 커널임
    - 커널 작업을 수행하고 있어도 언제든 다른 thread에게 preempt될 수 있음. (인터럽트 비활성화를 하지 않는 한)
    - 대부분은 interrupt state를 수정할 일이 없지만, kernel thread와 external interrupt handler(외부 인터럽트 처리기)를 synchronize하기 위해서 사용함.
    - 코드:`void thread_unblock (struct thread *);`, `void thread_yield (void);`
        - 아래 코드처럼 thread list 처리 도중에 발생하면 에러가 생길 수 있으므로 전 후로 비활성화 하는 모습을 볼 수 있다.
- **tick 증가 조건 탐색하기**
    - 매번 `void thread_tick (void)`이 호출됨.
    - 호출 주체는 `static intr_handler_func timer_interrupt`이다.
        - 타이머 인터럽트를 받으면 ticks을 1증가하고 thread_tick 호출함.
        - 아마 이걸 수정해서 thread가 활동하고 있는 tick을 세야 할 수도 있을 듯?
    - 배경 정보
        - AI랑 이야기하며 찾은거라 KAIST 기준인지 아닌지는 확실하지 않음.
        - Pintos가 동작하는 혹은 애뮬레이팅한 환경 Intel 8254 PIT은 클럭 카운트를 세서 약 10ms마다 OUT 핀을 토글하여 하드웨어 인터럽트를 보냄.
- **"interrupt handler는 sleep할 수 없으므로 일반적인 lock을 사용할 수 없다." 의 의미**
    - 인터럽트 핸들러는 자기만의 스레드가 아닌, 다른 스레드 실행 도중에 끼어든 코드 조각임. (그냥 jump한 거, 인터럽트당한 스레드의 커널 스택 위에서 실행됨)
        - 핸들러 자신은 스레드가 아니므로 sleep해도 복귀할 자기 컨텍스트가 없음.
        - 다만 인터럽트당한 스레드 정보는 스택을 통해 알 수 있어서, 그 스레드를 yield시키는 건 가능함.
        - 그래서 스레드 스위치가 필요한 경우엔 핸들러 본체에서 직접 하지 않고, 핸들러 본체가 끝난 뒤 디스패처(`intr_handler`)가 마지막에 처리함.
            - 인터럽트 처리가 완료되었으므로 기존 스레드로 실행을 계속 할건지 다른 스레드로 넘길건지 결정.
            - `intr_handler`의 `yield_on_return` 참고
    - 따라서 sleep하는 동기화 수단(일반 lock, semaphore의 down 등) 대신 spinlock이나 `intr_disable()`을 씀.
        - (다만 Pintos는 싱글 프로세서라 핸들러와의 race는 `intr_disable`만으로 충분함. spinlock은 Pintos엔 없음.)
- **코드 분석하면서 알게 된 유용한 패턴**
    - 함수가 인터럽트 지원해야 하는 경우 / 아닌 경우를 확실하게 구분하기
        - 왜냐면 인터럽트 처리 도중이면 sleep같은 스케줄링 기능을 못 씀.
        - `ASSERT`에 `intr_context ()`를 넣어서 이게 핸들러에 의해 호출되는 상황인지 빠르게 검증하기
        - `ASSERT (intr_get_level () == {INTR_OFF 또는 INTR_ON} );`으로 인터럽트 활성화 상태 확인하기
