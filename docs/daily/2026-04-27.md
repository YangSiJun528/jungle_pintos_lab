### 우선순위 스케줄링 TODO로 구현 구상

이전의 계획과 다르게 정렬 상태를 유지하지 않기로 했는데 사고 흐름이 다음과 같음.

#### 정렬 상태를 유지할만한데?

의사코드 짜고, 다시 요구사항 보면서 정리하는데, 이전에 조사했을 때랑 다르게 정렬 상태를 유지하는게 좋다는 결론에 도달함.

왜냐면 `thread_set_priority()`는 본인의 상태를 변경하는건데, 

세마포나 컨디션 변수를 호출하는 작업을 수행하는 경우, `ready_list`에 들어가는게 아니라, 
`waiters` list에서 별도로 관리되고, 상태도 `THREAD_BLOCKED`으로 바뀜. 

따라서 외부에서 바뀔 일이 없음. 

#### Priority Donation이 들어가면?

대신, 우선순위 도네이션이 되면 이야기가 달라지는데, 외부에서 수정될 수 있고, 그럼 그 때마다 정렬 상태를 유지해줘야 함.

(FAQ 문서의 "Can a thread's priority change while it is on the ready queue?" 참고하기.)

근데 그거는 구현하면서 함수로 빼거나 하면 될듯? 그냥 max를 고려했는데 락 추가(재정렬, 그냥 냅둠) + 다음 작업 구하기(바로 뽑기 or max) 

이러면 생각보다 다음 작업 구하는게 더 빨라야하기도 하고... AI랑 이야기 더 충분한 문맥을 주고 하니까 이걸 추천해줌.

사실 귀찮긴 한데, `list_insert_ordered` 쓰는게 생각보다 복잡하지 않아서 그냥 추천한대로 구현 할 듯?

### Pintos의 컨디션 변수 구현 방법 설명

컨디션 변수

```
condition variable
└── waiters list
    ├── waiter A: semaphore value = 0
    ├── waiter B: semaphore value = 0
    └── waiter C: semaphore value = 0 
```

스레드를 종료하고 깨우는 역할을, 이미 구현된 semaphore가 수행하도록 한다.

따라서 사용자가 `cond_wait(cond, lock)` 시마다 새로운 세마포가 생긴다.
즉, 대기하는 스레드와 세마포는 서로 1:1 관계로 묶여있고 봐도 될 듯?

하려면 그냥 semaphore의 내부 로직과 비슷한 로직을 사용해서 개발 할 수 있을 듯?

근데 편의를 위해서 사용했다고 보임.
