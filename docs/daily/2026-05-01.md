### User program - 이동석 코치님

초반(Argument passing)이 많이 어려움. 의존성이 큼.

그 뒤에는 시스템 콜 구현하는거, 난이도 다양함.

테스트케이스 많음. 거의 80개, 이해하기 어려운 것도 많음.

팀원들 간의 협업 중요.

개발한 프로젝트 1의 기능에 프로젝트 2가 영향을 받을 수도 있음. (버그만 없으면 어느정도 ㄱㅊ)
동작이 잘 안되는 코드면 사용하지 않는게 좋음.

1주차에 한건, 커널 프로그램 자체의 함수를 실행한 것임. 즉, 테스트도 그냥 함수 호출이지 커널이라는 의미에 맞지 않음.

이제는 유저 프로그램과 같은 걸 실행해서 동작시키는 기능을 만들어야 함.
이제 테스트코드도 유저 레벨의 별도 프로그램으로 관리될 것임.
= 커널의 기능이 작아짐(테스트 로직 제거)

실제로 보면 main 함수가 있음. (테스트가 독립적인 실행파일으로서 존재하게 됨)

프로세스: 실행파일을 실행하는 거.
스레드: 프로세스가 너무 커서 새로 나온 개념, 더 작은 단위로 프로세스를 분리.

멀티스레드ed 프로세스?는 제공하지 않음. 멀티코어 같은거.

멀티 프로세스인데, 여기선 프로세스를 스레드로 구현? 되어있어서 용어를 섞어서 씀.

prcess, systmem-call, exception 쪽만 봐도 충분

나머진 공부하는건 비추 일단 시간이 없으니까. 핵심을 이해해야 함.

파일시스템 부분도 읽을 필요 없음. 프로그램은 파일에 저장되어 있어서 필요한 것.

OS가 파일을 해석하는 방법이 파일시스템

FAT, NTFS, 등등...

근데 우리는 파일시스템 구현 안했음. (프로젝트 4에 FAP 만듦.)

그래서 여기서는 간단하게 더미로 만들어두었음. 그래서 여러 제한이 있음.

이름 길이 제한, 폴더 없고, 트리 아니고, 파일 크기 제한되어있고, 동기화 방법 없음.

CPU의 모드 컨셉 설명

범용 목적 커널에선 사용자의 동작을 제어해야 함. 그래서 CPU와 OS에서 모드를 변경하기.

중요한 작업이 필요하면 커널로 가서 모드를 바꾸고 수행해야 함.

이러면 유저 레벨에서 위험한 걸 못하고, 커널만 잘 짜이면 터지지 않게 됨.

syscall로 사용자 모드에서 커널 모드로 이동
iretq로 커널에서 사용자 모드로 이동?

(아주 오래된, or 현재의 작은 cpu에는 이런 기능이 없기도 함.)

커널 모드에선 공유 자원, 보안 관련 동작을 수행

공유 자원은 모든 프로세스가 사용하는 메모리, 키보드, 화면, 저장장치 등임.

printf도 내부적으로 시스템 콜을 호출함. 근데 테스트코드에서 다 printf를 씀.

이러면 printf 디버깅이나 테스트도 하다가 뻗어버림.

그래서 printf기 쓰는 시스템 콜부터 구현하는걸 추천

파일에 읽고 쓰는걸로 화면에 그리고 그런 작업도 수행됨(추상화)

그리고 그 파일 중, 0, 1, 2 파일(fd)는 고정되어있음.

1번이 printf와 같은 곳에서 필요한 일반 출력에 쓰는 것임.

이거부터 해야 함.

정리

1. OS가 수행하는 유저 프로그램을 실행하는 것이 목표
2. 어떻게 프로그램이 실행되는지 알아야 함
    - 실행파일의 포맷
    - 실행 프로세스(기술적인거 말과 그 과정을 의미함)
3. Pintos에서 모든 기능을 제공하진 않아서 제약이 있음
4. 인자를 스택에 받고 실행하는 규칙을 지켜야 함
5. 시스템 콜도 구현해야 함 - printf를 실행할 수 있는 시스템콜 먼저
    - 나중에 구현하겠지만, fork, exec, wait 이 좀 어려움
        - 구현 시 락이나 세마포 등을 사용해서 동기화가 필요함
6. 5번까지 하고 나면, 테스트 케이스 실행이 안될거임
    - process_wait이 구현이 안되어 있어서 그냥 종료되는데
    - 이러면 다른 스레드 실행하고 OS를 죽여버려서 항상 실패할거임
    - 이거 찾는데 사람들이 많이 해매서 말은 해줌.
7. syscall_handler는 switch가 되었든 뭐가 되었든 나눠서 실행해야 함.
8. 어려워하는 테스트:
    - oom 테스트 케이스
        - 해석을 잘못 해서 그런거임.
        - 이거가지고 4일 밤 새는 경우도 봤는데, 예전 선배 기수에서는 사람들이 잘못 짠 코드를 그대로 써서 문제가 생겼던거임.
    - sync 구현 문제로 인한 실패
        - 스레드 구현, 원본이 잘못되어 있는 경우
        - 될 떄도 있고 안될 때도 있음
        - 대부분 이러면 동기화 구현 문제
9. 추천 순서
    - Argument Passing 빨리
    - 시스템 콜 file 쪽은 디팬던시 없는 거 끼리 나눠서 처리
    - 테스트코드가 한 기능에 대한 여러 엣지 케이스가 있어서 AI한테 부탁해서 작업 분담하는게 좋을듯
