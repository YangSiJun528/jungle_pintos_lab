### `load_segment`의 파일 로드 페이지들은 `VM_ANON`이여야 할까? - 보류, 고민

이전에 물어봤던 다른 팀에서 구현하면서 찾고 알려줬는데, 
`load_segment`의 `vm_alloc_page_with_initializer`은 `VM_ANON`인게 맞음. 

`VM_FILE`은 swap 전략이 달라져서 안된다고 함.

생각해보면 exec 파일의 경우, deny_write 되서 어차피 쓸 수도 없고,

그리고 32bit 기반 카이스트 자료에선 BIN, ANON, FILE 타입으로 더 명확하게 나뉨.

근데? 흠... 그러면 load_segment에서 생성하는 타입을 `VM_FILE`을 못 쓰는거 아닌가?

### AI 써서 붙이면서 조금 바뀐 부분들 + 수정한 버그, 개선들

1. 호출 흐름이 이런 식이라, `lazy_load_segment()`에선 `vm_do_claim_page()`을 호출하면 중복 호출임.

```
page_fault() 
→ vm_try_handle_fault() 
→ vm_do_claim_page(page) 
→ swap_in(page, frame->kva) 
→ uninit_initialize() 
→ lazy_load_segment(page, aux) 
```

2. 위의 `load_segment`의 파일 로드 페이지들은 `VM_ANON`이여야 한다는 문제.

3. 기존 mmap 검사 로직 개선 
  - length, offset 오버플로우 검사 추가 (적절한 영역인지 검사)

4. page 단위 file 복제 시, leak 발생 가능
   - load_segment에서 페이지마다 파일 복사가 발생함.
   - file 기반 destory 함수 구현에선 free를 해주는데,
   - uninit 상태에서는 처리를 안해주고 있어서 leak 발생했었음.
   - 해당 처리 추가하여 개선

5. (아직 안한 개선 포인트) 4번의 방식이 그리 좋지는 않다고 함. page단위보다 mmap 단위가 더 직관적임
   - 특히 duplicate 되서 내부 ref 카운트가 늘어나는데, 
   - file 전체를 보는 게 아닌게 카운트가 늘어난다는게 좀 이상한거 같음.
