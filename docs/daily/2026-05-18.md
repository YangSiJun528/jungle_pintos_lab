### `load_segment`의 파일 로드 페이지들은 `VM_ANON`이여야 할까? - 보류, 고민

`load_segment`의 `vm_alloc_page_with_initializer`은 `VM_ANON`인게 맞음.

### AI 써서 붙이면서 조금 바뀐 부분들 + 수정한 버그, 개선들

1. 호출 흐름이 이런 식이라, `lazy_load_segment()`에선 `vm_do_claim_page()`을 호출하면 중복 호출임.

```
page_fault() 
→ vm_try_handle_fault() 
→ vm_do_claim_page(page) 
→ swap_in(page, frame->kva) 
→ uninit_initialize() 
→ lazy_load_segment(page, aux) 
```

2. 위의 `load_segment`의 파일 로드 페이지들은 `VM_ANON`이여야 한다는 문제.

3. 기존 mmap 검사 로직 개선 
  - length, offset 오버플로우 검사 추가 (적절한 영역인지 검사)

4. page 단위 file 복제하는 패턴은 좀 별로임. 그리고 실수로 leak 발생하고 있음
   - load_segment에서 페이지마다 파일 복사가 발생함.
   - file 기반 destory 함수 구현에선 free를 해주는데,
   - uninit 상태에서는 처리를 안해주고 있어서 leak 발생했었음.
   - 해당 처리 추가하여 개선

5. (아직 안한 개선 포인트) 4번의 방식이 그리 좋지는 않다고 함. page단위보다 mmap 단위가 더 직관적임
   - 특히 duplicate 되서 내부 ref 카운트가 늘어나는데, 
   - file 전체를 보는 게 아닌게 카운트가 늘어난다는게 좀 이상한거 같음.

생에주기에 문제가 있었음.

`load_segment()` 그대로 가져다 쓸 수 있다고 생각했는데, 그것도 위 4번 문제로 어려웠고.

그래서 mmap에선 `load_segment()` 대신에 별도 로드 함수를 사용하게 함.

따라서 `load_segment()`의 `vm_alloc_page_with_initializer`에선 `VM_ANON`을 사용하도록 수정함.

그리고 생애주기는 위의 4번에서 말한거처럼 생애주기로 따지면 애매하긴 한데, 
hash destroy로 page를 제거하고 있고, 이 때 페이지 순서를 보장하지 않으므로 
각 page가 file을 duplicative 해서 가지고 있는게 더 기존 구조에 남음.

아니면 별도의 ref cnt 기반의 cleanup 함수가 필요할거 같음.  
구조체를 생성하고, cnt가 0이면 head부터 쭉 제거하는거,

이게 사실 정배같은데,

뭐... 일단 빠르게 swap과 file system까지 흝어보고 싶어서 일단 이런 구현을 채택.

`do_mmap()`에서 `load_segment()`과 비슷한 순회 + 페이지 등록 작업을 수행하는데,

aux로 넘길 때, file을 복사해서 넘겨준다는데 차이점.

file의 종료 or unix 스타일 제거를 위해서 내부적으로 ref cnt를 쓴다는 점을 이용해서 야매로 구현되어있음.

### [AI 글] read/write syscall의 유저 버퍼를 참고하면 fault가 발생할 수 있음

현재 read/write syscall은 filesys_lock을 잡은 상태에서 유저 버퍼를 file_read/write에 그대로 넘긴다.

문제는 파일시스템 내부가 그 유저 주소에 직접 접근하다가 lazy page fault가 날 수 있다는 점이다.

read/write syscall
-> filesys_lock 획득
-> file_read/write가 user buffer 접근
-> page fault
-> VM lazy load / mmap swap-in
-> 다시 filesys_lock 필요

근본적으로는 파일시스템에 유저 주소를 직접 넘기지 말고, syscall에서 user buffer와 kernel buffer 사이를 먼
저 복사한 뒤 file_read/write는 kernel buffer로만 수행하는 구조가 더 안전하다.

리눅스에선 이런 식으로 처리함.

- filesystem이 user pointer를 신뢰하지 않아 아무렇게나 직접 접근하지 않음
- user memory 접근은 copy_from_user, copy_to_user, iov_iter 같은 uaccess 계층을 통해 함
- 그 과정에서 page fault가 날 수 있음을 전제로 설계함
- fault가 나면 page를 가져오거나, fault 불가능한 context면 실패 처리함
- direct I/O처럼 복사를 줄여야 할 때는 user page를 pin 해서 I/O 중 사라지지 않게 함

현재 코드에서는
`bool must_release = !lock_held_by_current_thread (&filesys_lock);   `
같은 방법을 사용하여 임시로 해결해보려고 할 수 있으나, 코드가 더러워지기도 하고, 
일단은 저 문제는 고려하지 않기로 한다.
