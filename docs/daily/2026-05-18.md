### [AI 글] read/write syscall의 유저 버퍼를 참고하면 fault가 발생할 수 있음

현재 read/write syscall은 filesys_lock을 잡은 상태에서 유저 버퍼를 file_read/write에 그대로 넘긴다.

문제는 파일시스템 내부가 그 유저 주소에 직접 접근하다가 lazy page fault가 날 수 있다는 점이다.

read/write syscall
-> filesys_lock 획득
-> file_read/write가 user buffer 접근
-> page fault
-> VM lazy load / mmap swap-in
-> 다시 filesys_lock 필요

근본적으로는 파일시스템에 유저 주소를 직접 넘기지 말고, syscall에서 user buffer와 kernel buffer 사이를 먼
저 복사한 뒤 file_read/write는 kernel buffer로만 수행하는 구조가 더 안전하다.

리눅스에선 이런 식으로 처리함.

- filesystem이 user pointer를 신뢰하지 않아 아무렇게나 직접 접근하지 않음
- user memory 접근은 copy_from_user, copy_to_user, iov_iter 같은 uaccess 계층을 통해 함
- 그 과정에서 page fault가 날 수 있음을 전제로 설계함
- fault가 나면 page를 가져오거나, fault 불가능한 context면 실패 처리함
- direct I/O처럼 복사를 줄여야 할 때는 user page를 pin 해서 I/O 중 사라지지 않게 함

현재 코드에서는
`bool must_release = !lock_held_by_current_thread (&filesys_lock);   `
같은 방법을 사용하여 임시로 해결해보려고 할 수 있으나, 코드가 더러워지기도 하고, 
일단은 저 문제는 고려하지 않기로 한다.

### swap 개념 보기

PTE에 있는 플래그 비트
- 더티 비트: 메모리의 값을 쓸 때 CPU(정확히는 MMU)가 1로 설정.
- 엑세스 비트: 메모리의 값을 읽을 때 CPU(정확히는 MMU)가 1로 설정.

엑세스 비트는 주기적으로 OS가 시간 체크해서 꺼주고, swap out 할 데이터를 찾을 때 쓰기도 하지만.

핀토스에서 해주진 않는거 같음.  

암튼 그것과 별개로 프레임 테이블을 LRU와 비슷한 알고리즘으로 관리해서 swap out할 프레임을 정해야 함.

그 프레임의 더티 비트가 켜져있으면 디스크에 저장해두어야 함. 그리고 프레임을 nullify해서 완료했음을 알려줘야 함.

그리고 swap 가능한 공간은 선형적으로 관리되는데,   
그 범위가 사용 가능한지 알기 위해서 bitmap을 사용하여 데이터를 관리할 수 있음.

## 가상 메모리와 PTE 정리 

가상→물리 주소 변환은 **OS(소프트웨어)**, **MMU(CPU 내부 하드웨어)**, **TLB(MMU 내부 캐시)** 세 주체의 협업으로 이루어진다.

### 역할 분담

**OS**
- 페이지 테이블을 메모리에 구축하고 PTE의 모든 필드(PFN, R/W/X, U/S, present 등)를 채운다.
- 페이지 테이블 베이스 주소를 레지스터(x86 `CR3`, ARM `TTBRn`)에 적재 → 컨텍스트 스위치 시 갱신.
- 페이지 폴트 처리, 스왑, COW, demand paging 등 모든 정책 결정.
- PTE 수정 후 **TLB 무효화** 책임 (`invlpg` / `TLBI`, 멀티코어는 TLB shootdown).

**MMU (CPU 다이 내부 하드웨어 블록)**
- CR3/TTBR을 읽어 페이지 테이블을 워크하며 가상→물리 변환 수행.
- 권한 검사, 위반 시 페이지 폴트 발생시켜 OS로 제어 이전.
- **A/D 비트의 0→1 설정만 자동으로 수행** (atomic RMW). 
  - 하지않는 것: 1→0 클리어 및 그 외 필드 수정.
- 변환 결과를 TLB에 캐싱.

**TLB**
- MMU 내부 캐시. 가상→물리 변환 결과 저장.
- 다단계 페이지 워크(x86-64는 4~5단계) 비용을 회피.

### PTE의 본질

- PTE는 그냥 메모리에 저장된 정수다. OS는 일반 load/store로 자유롭게 읽고 쓸 수 있다.
- 페이지 테이블은 다단계 트리 구조.
- 레지스터에 들어가는 건 페이지 테이블 베이스 포인터

### OS의 PTE 구성 방식

- **Demand paging**: 미리 다 만들지 않고, 폴트 발생 시점에 lazy하게 채움.
  - 이를 위해 보조 페이지 테이블 정보를 별도로 관리 
- 폴트 핸들러는 VMA(영역 메타데이터)를 조회해 합법적 접근인지 판단:
   - ELF `.text` → R+X, `.rodata` → R, `.data`/힙/스택 → R+W
   - 매핑된 파일, 익명 메모리 등 출처별 권한 적용
- 합법이면 물리 프레임 할당 후 PTE 작성, 불법이면 SIGSEGV.

### 변환 흐름

1. CPU 코어가 가상주소로 메모리 접근 요청
2. MMU가 TLB 조회 → 히트면 즉시 물리주소 반환
3. 미스면 페이지 워크 → 권한 검사 → A/D 비트 갱신 → TLB 캐싱
4. present=0 또는 권한 위반 시 페이지 폴트 → OS 핸들러
5. OS가 PTE 채우거나 SIGSEGV

### (추가) PTE 주요 필드

- PFN (Page Frame Number): PTE의 본체. 이 가상 페이지가 매핑된 물리 프레임 번호.
- R/W (Read/Write): 쓰기 허용 여부
- X (eXecute) / NX (No-eXecute): 명령어 실행 허용 여부, 대부분 .text 일때만 X
- U/S (User/Supervisor): 접근 가능한 권한 레벨. U=1이면 유저 모드도 접근 가능, U=0이면 커널만.
- Present (또는 Valid): PTE 자체가 유효한지. 0이면 매핑 없음. (스왑 아웃, 미매핑 등일 때 0)

## Pintos/x86-64 Page Table 핵심 정리

### 1. 가상주소 구조

Pintos KAIST x86-64 기준으로 4KB page를 쓰면 virtual address는 이렇게 나뉩니다.

```text
47..39  PML4 index   9 bits
38..30  PDPT index   9 bits
29..21  PD index     9 bits
20..12  PT index     9 bits
11..0   page offset 12 bits
```

즉:

```text
9 + 9 + 9 + 9 + 12 = 48 bits
```

하위 12비트 offset은 page table entry에 저장하지 않습니다. 최종 physical address를 만들 때 그대로 붙습니다.

```text
physical address = physical frame base + offset
```

### 2. Page walk는 스캔이 아니라 인덱싱

CPU는 page table을 선형 탐색하지 않습니다. VA의 각 9비트 구간을 index로 사용합니다.

```text
CR3
 -> PML4[index]
    -> PDPT[index]
       -> PD[index]
          -> PT[index]
             -> PTE
                -> physical frame + offset
```

각 page table page는 4KB이고, entry 하나는 8바이트입니다.

```text
4096 / 8 = 512 entries
```

그래서 각 index가 9비트입니다.

### 3. Entry의 의미

4KB page 기준:

```text
PML4E -> PDPT page의 physical base address + flags
PDPTE -> PD page의 physical base address   + flags
PDE   -> PT page의 physical base address   + flags
PTE   -> data frame의 physical base address + flags
```

즉 중간 entry도 값을 가집니다. 다만 최종 data frame을 가리키는 것은 PTE이고, 중간 entry는 다음 page table page를 가리킵니다.

### 4. Entry 하위 12비트가 flags인 이유

page table page와 frame은 모두 4KB aligned입니다. 따라서 물리주소 하위 12비트는 항상 0입니다.

```text
0x12345000
        ^^^
        항상 0
```

그래서 entry는 대략 이렇게 구성됩니다.

```text
bits 12..51 : physical base address
bits 0..11  : flags
```

예:

```text
PDPTE = 0x0000000012345007

주소 부분 = 0x0000000012345000
flags    = 0x007
```

### 5. PTE는 VA를 저장하지 않음

PTE 안에는 “내가 어떤 VA에 대응되는가”가 저장되지 않습니다.

그 이유는 page table 안에서의 위치가 VA를 이미 암시하기 때문입니다.

```text
PML4[0] -> PDPT[0] -> PD[2] -> PT[3]
```

이 경로 자체가 특정 virtual page를 의미합니다.

PTE에는 다음만 있으면 됩니다.

```text
physical frame base address
flags
```


### 6. 다단계 page table을 쓰는 이유

48-bit VA 전체를 flat page table로 만들면:

```text
virtual page 수 = 2^48 / 2^12 = 2^36
PTE 크기 = 8 bytes
필요 공간 = 2^36 * 8 = 512 GiB
```

프로세스 하나당 page table만 512GiB가 필요해집니다.

그래서 x86-64는 필요한 하위 table만 할당하는 sparse radix tree 구조를 씁니다.

```text
PML4
 └─ PDPT
     └─ PD
         └─ PT
             └─ PTE
```


### 7. 각 레벨이 커버하는 범위

```text
PTE 1개       -> 4KB
PT page 1개   -> 2MB
PD page 1개   -> 1GB
PDPT page 1개 -> 512GB
PML4 page 1개 -> 256TB
```

같은 2MB 안의 page들은 같은 PT page를 공유합니다.

### 8. CPU와 OS의 역할

CPU가 하는 일:

```text
CR3에서 PML4 physical address 확인
VA를 index로 쪼개 page walk
flags 검사
A/D bit 설정
실패 시 page fault 발생
TLB에 변환 결과 캐시
```

OS가 하는 일:

```text
page table page 할당
physical frame 할당
PTE 설정
page fault 처리
lazy loading
stack growth
swap in/out
mmap
SPT 관리
```

CPU는 page table page를 자동 생성하지 않습니다. 없으면 page fault만 냅니다.

### 9. PML4/page table과 SPT의 차이

PML4/page table:

```text
CPU가 직접 쓰는 하드웨어 형식 자료구조
VA page -> physical frame 매핑
present/writable/user/accessed/dirty/NX 등 저장
```

SPT, supplemental page table:

```text
OS가 page fault 처리를 위해 쓰는 소프트웨어 자료구조
이 VA가 합법적인가
VM_ANON / VM_FILE / VM_UNINIT 여부
lazy load 정보
swap slot 정보
mmap 정보
struct page / struct frame 연결
```

즉:

```text
PML4/page table = CPU용 주소 변환 자료구조
SPT             = OS용 VM 메타데이터 자료구조
```

### 10. 새 프로세스의 PML4

Pintos에서 새 process의 PML4는 처음부터 kernel mapping을 포함합니다.

개념적으로:

```c
pml4 = palloc_get_page(...);
memcpy(pml4, base_pml4, PGSIZE);
```

결과:

```text
new process PML4
 ├─ user 영역: 비어 있음
 └─ kernel 영역: 이미 매핑됨
```

복사되는 것:

```text
PML4 root page 안의 entry 값들
```

복사되지 않는 것:

```text
kernel code/data
physical memory
kernel direct mapping의 하위 PDPT/PD/PT page들
```

즉 여러 process의 PML4가 같은 kernel-side 하위 page table을 공유합니다.

### 11. Pintos의 physical memory direct mapping

x86-64에서는 physical address를 직접 dereference할 수 없습니다. 그래서 Pintos는 kernel virtual memory를 physical memory에 1:1 매핑합니다.

```text
kernel virtual address = KERN_BASE + physical address
physical address       = kernel virtual address - KERN_BASE
```

예:

```text
physical 0x00000000 -> virtual KERN_BASE + 0x00000000
physical 0x00001234 -> virtual KERN_BASE + 0x00001234
physical 0x00100000 -> virtual KERN_BASE + 0x00100000
```

### 12. page table entry에는 physical address를 넣어야 함

중요한 마지막 정리입니다.

CPU가 page walk할 때 entry 안의 주소는 **physical address**로 해석합니다.

```text
PML4E  안에는 PDPT page의 physical address
PDPTE  안에는 PD page의 physical address
PDE    안에는 PT page의 physical address
PTE    안에는 data frame의 physical address
```

하지만 커널 C 코드는 physical address를 직접 접근할 수 없습니다. 커널은 page table page를 kernel virtual address로 접근합니다.

그래서 변환이 필요합니다.

```text
entry에 저장할 때:
  kernel virtual address -> physical address
  vtop(kva)

entry를 따라가서 C 포인터로 접근할 때:
  physical address -> kernel virtual address
  ptov(pa)
```

핵심:

```text
커널이 조작할 때는 KVA
CPU entry에 저장할 때는 PA
```

### 13. 초기 page table 생성 흐름

초기 page table은 단계적으로 만들어집니다.

```text
1. 부트/초기 long mode 진입용 최소 page table
   - 커널 코드를 실행할 수 있을 정도만 구성

2. Pintos kernel용 base_pml4 구성
   - kernel direct mapping 구성
   - KERN_BASE + pa -> physical pa

3. user process 생성 시 pml4_create()
   - 새 PML4 page 생성
   - kernel mapping 포함
   - user mapping 없음

4. ELF loader / VM 코드가 user mapping 추가
   - code/data/stack
   - pml4_set_page()
   - vm_do_claim_page()
```

### 14. 작은 프로그램의 page table 비용

가장 단순하게:

```text
code page  1개
stack page 1개
```

라고 보면, 코드와 스택은 멀리 떨어져 있으므로 하위 page table을 공유하지 못할 수 있습니다.

대략:

```text
PML4 root             4KB
code용 PDPT/PD/PT     12KB
stack용 PDPT/PD/PT    12KB
--------------------------
page table metadata   약 28KB
```

실제 user frame:

```text
code frame   4KB
stack frame  4KB
----------------
약 8KB
```

작은 프로그램에서는 실제 데이터보다 page table metadata가 클 수 있습니다.


### 15. Huge page

지금까지는 **4KB page 기준**입니다.

```text
4KB page:
  PML4E -> PDPTE -> PDE -> PTE -> 4KB frame
```

x86-64는 더 큰 page도 지원합니다.

```text
2MB huge page:
  PML4E -> PDPTE -> PDE -> 2MB frame

1GB huge page:
  PML4E -> PDPTE -> 1GB frame
```

즉 huge page에서는 중간 entry가 다음 page table을 가리키지 않고 큰 physical frame을 직접 매핑합니다.

구분은 `PS(Page Size)` bit로 합니다.

```text
PDPTE.PS = 1 -> 1GB page 직접 매핑
PDE.PS   = 1 -> 2MB page 직접 매핑
PS = 0        -> 다음 레벨 page table로 이동
```

메모리 절약 효과:

```text
1GB를 4KB page로 매핑:
  PTE 262,144개 필요
  PT page 512개 필요
  PT metadata 약 2MB

1GB를 2MB huge page로 매핑:
  PDE 512개 필요
  PT page 불필요
  PD page 1개로 처리
```

장단점:

```text
장점:
  page table 메모리 감소
  page walk 단계 감소
  TLB 효율 증가

단점:
  내부 단편화 증가 가능
  작은 단위 권한 설정 어려움
  eviction/swap 단위가 커짐
  VM 구현 복잡도 증가
```

## 최종 압축 결론

```text
x86-64/Pintos page table은 VA를 9/9/9/9/12로 쪼개는 4단 radix tree다.

CPU는 CR3에 있는 PML4 physical address에서 시작해 PML4E -> PDPTE -> PDE -> PTE를 따라간다.

각 entry는 64비트이고, 다음 table 또는 최종 frame의 physical base address와 flags를 저장한다.

entry 안에는 VA를 저장하지 않는다. VA는 page table 경로와 entry 위치로 암시된다.

커널은 page table page를 KVA로 조작하지만, entry에는 PA를 저장해야 하므로 vtop()을 쓴다.
반대로 entry에서 얻은 PA를 C 포인터로 접근하려면 ptov()를 쓴다.

초기에는 부트용 최소 page table이 만들어지고, 이후 base_pml4에 kernel direct mapping이 구성된다.
새 process의 PML4는 base_pml4의 kernel mapping을 포함한 상태로 생성되고, user mapping은 이후 loader/VM 코드가 추가한다.

PML4/page table은 CPU용 주소 변환 구조이고, SPT는 OS가 page fault, lazy loading, swap, mmap, stack growth를 처리하기 위한 VM 메타데이터 구조다.

Huge page는 PDE/PDPTE가 다음 테이블 대신 큰 frame을 직접 가리키게 해서 page table 비용과 page walk 비용을 줄이는 기능이다.
```
