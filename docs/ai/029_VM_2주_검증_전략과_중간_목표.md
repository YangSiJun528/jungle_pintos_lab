# Pintos VM 2주 검증 전략과 중간 목표

이 문서는 Pintos Project 3 `vm`을 AI 없이 팀원들이 2주 동안 진행할 때, 어디까지 해야 테스트로 검증할 수 있는지와 어떤 순서로 목표를 잡는 것이 현실적인지 정리한다.

구현 코드나 붙여 넣을 수 있는 구현안은 포함하지 않는다. Copy-on-write는 제외한다.

## 한 줄 결론

`SPT + frame claim + uninit/anon + executable lazy loading + page fault + initial stack`이 연결되기 전까지는 VM 테스트에서 의미 있는 PASS가 거의 안 나올 수 있다.

하지만 이것이 “아예 검증할 수 없다”는 뜻은 아니다. 컴파일, kernel panic 위치, `.output`, `.errors`, `build/results`, 특정 테스트의 진행 로그로 계속 디버깅할 수 있다.

2주 목표는 전체 VM 완성이 아니라, 먼저 `lazy-*`와 `pt-grow-*`까지 안정화하고, 시간이 남으면 mmap normal을 붙이는 식으로 잡는 것이 현실적이다. swap과 fork/swap 통합은 후순위로 둔다.

## “테스트 결과가 안 나온다”의 정확한 의미

팀에서 말하는 “특정 영역 이전까지 테스트 결과가 안 나온다”는 말은 절반만 맞다.

### 맞는 부분

VM은 초반 공통 기반이 길다. 다음 흐름이 연결되기 전에는 유저 프로그램 실행 자체가 자주 깨질 수 있다.

- supplemental page table에서 fault 주소의 page를 찾는다.
- frame을 `PAL_USER`로 할당하고 page와 연결한다.
- uninit page가 첫 fault에서 실제 anon/file page로 초기화된다.
- executable segment가 lazy loading으로 등록된다.
- page fault handler가 SPT lookup 후 claim한다.
- initial stack이 VM 방식으로 올라온다.

이 흐름이 완성되기 전에는 `tests/vm`에서 PASS가 거의 없거나, 대부분 kernel panic/timeout/early exit로 끝날 수 있다.

### 틀린 부분

“아예 결과가 없다”는 말은 정확하지 않다.

`TESTING.md` 기준으로 Pintos 테스트는 실패해도 보통 다음 파일을 남긴다.

- `pintos/vm/build/results`
- 개별 테스트의 `.output`
- 개별 테스트의 `.errors`
- 개별 테스트의 `.result`

단, 컴파일 실패, kernel panic, timeout, 인터럽트처럼 실행이 끝까지 가지 못하면 `.result`가 없을 수 있다. 이 경우에도 `.errors`나 make 출력, `.output` 일부가 디버깅 단서가 된다.

## Vn별 테스트 가능성과 검증 방식

`Vn`은 팀이 만든 작업 분해 단위이고, Pintos 테스트는 `lazy-*`, `pt-*`, `mmap-*`, `swap-*`처럼 기능/행동 기준으로 되어 있다. 따라서 모든 `Vn`마다 1:1로 대응되는 PASS 테스트가 있는 것은 아니다.

정확히는 다음처럼 봐야 한다.

| 단계 | 단독 테스트 가능성 | 주 검증 방식 |
|---|---:|---|
| V0 Build/Template | 높음 | `make -C "$PINTOS_ROOT/vm"` 빌드 성공 |
| V1 SPT Core | 낮음 | SPT key, insert/find, 중복 방지 contract 확인 |
| V2 Frame Claim | 낮음 | `PAL_USER` 할당, frame-page 역참조, pml4 mapping contract 확인 |
| V3 Uninit/Anon | 낮음 | `VM_UNINIT` 등록, initializer 흐름, destroy 최소 contract 확인 |
| V4 Executable Lazy Loading | 중간 이하 | V5/V6와 붙은 뒤 `lazy-*` 로그로 확인 |
| V5 Page Fault Core | 중간 | `lazy-anon`, `lazy-file`, `pt-bad-addr`, `pt-write-code` 시도 |
| V6 Initial Stack | 중간 | user program 실행 진행도, `lazy-*`, Project 2 회귀 관찰 |
| V7 Stack Growth | 높음 | `pt-grow-stack`, `pt-grow-stk-sc`, `pt-big-stk-obj`, `pt-grow-bad` |
| V8 SPT Copy/Cleanup | 중간 | `page-parallel`, `page-merge-*` 일부. fork 흐름 의존 |
| V9 mmap Validation | 높음 | `mmap-null`, `mmap-misalign`, `mmap-zero-len`, `mmap-bad-fd*` |
| V10 File-backed Core | 중간 이하 | V11과 붙은 뒤 `mmap-read`, `lazy-file` |
| V11 mmap Normal | 높음 | `mmap-read`, `mmap-write`, `mmap-unmap`, `mmap-close` |
| V12 mmap Robust | 높음 | `mmap-over-*`, `mmap-clean`, `mmap-remove`, `mmap-ro`, `mmap-exit` |
| V13 Eviction Core | 낮음 | 단독 PASS 거의 없음. V14/V15의 선행 기반 |
| V14 Anonymous Swap | 높음 | `swap-anon`, `swap-iter` 일부 |
| V15 File-backed Swap | 높음 | `swap-file`, `mmap-shuffle`, `swap-iter` |
| V16 Fork/mmap/swap 통합 | 높음 | `mmap-inherit`, `swap-fork`, `page-merge-*` |
| V17 Regression | 높음 | COW 제외 VM 전체 회귀 |

요약하면 다음과 같다.

```text
V0~V4: 주로 build, code contract, panic 위치로 검증
V5~V6: 첫 의미 있는 VM 테스트 실행과 로그 검증 가능
V7~V12: 기능별 PASS 테스트로 검증 가능
V13: 다시 단독 테스트가 약한 기반 단계
V14~V16: swap/fork/mmap 통합 테스트로 검증 가능
```

## 검증 레벨

초반 `V1~V6`은 PASS/FAIL 하나로만 판단하면 진행 상황을 놓치기 쉽다. 검증을 세 단계로 나눈다.

### 1. 빌드 검증

항상 가장 먼저 확인한다.

```bash
make -C "$PINTOS_ROOT/vm"
```

여기서 실패하면 테스트 이전 문제다. 최근 변경한 header, prototype, include, struct field, conditional compile부터 확인한다.

### 2. Contract / invariant 검증

단독 PASS 테스트가 없는 티켓은 “이 함수와 구조가 지켜야 할 조건”을 완료 기준으로 둔다.

| 티켓 | 확인할 조건 |
|---|---|
| V1 SPT | 같은 page-aligned `va`가 중복 insert되지 않는다. |
| V1 SPT | `spt_find_page(spt, va)`가 unaligned 주소도 같은 page로 찾는다. |
| V1 SPT | 이후 copy/kill/mmap overlap에서 순회할 방법이 있다. |
| V2 Frame | frame은 user page용으로 `PAL_USER` pool에서 할당된다. |
| V2 Frame | `page->frame`과 `frame->page`가 서로 연결된다. |
| V2 Claim | pml4 mapping 뒤 user `va`가 frame `kva`로 연결된다. |
| V2 Claim | mapping 실패 시 frame/page 상태가 어중간하게 남지 않는다. |
| V3 Uninit | page가 처음에는 `VM_UNINIT`으로 SPT에 들어간다. |
| V3 Anon | fault 후 anon initializer가 호출될 수 있는 operations 구조다. |
| V3 Destroy | process exit 시 uninit/anon page가 최소한 누수 없이 정리될 경로가 있다. |
| V4 Lazy | `load_segment`가 즉시 file을 모두 읽지 않고 page별 lazy entry를 등록한다. |
| V4 Lazy | aux에 file offset, read bytes, zero bytes, writable 정보가 보존된다. |
| V5 Fault | not-present fault에서만 lazy claim을 시도한다. |
| V5 Fault | kernel address 접근과 read-only page write를 거부한다. |
| V5 Fault | invalid fault는 kernel panic이 아니라 정해진 종료/실패 경로로 간다. |
| V6 Stack | argument passing이 stack에 쓰기 전에 첫 stack page가 mapping되어 있다. |

이 표는 unit test가 아니라 코드 리뷰와 디버깅 체크리스트다. 초반에는 이 조건들이 실질적인 완료 기준이다.

### 3. 실행 로그 검증

PASS가 안 나와도 특정 테스트를 반복해서 “어디까지 진행됐는지”를 본다.

```bash
make -C "$PINTOS_ROOT/vm" build/tests/vm/lazy-anon.result
```

그 다음 다음 파일을 확인한다.

```bash
cat "$PINTOS_ROOT/vm/build/tests/vm/lazy-anon.output"
cat "$PINTOS_ROOT/vm/build/tests/vm/lazy-anon.errors"
cat "$PINTOS_ROOT/vm/build/tests/vm/lazy-anon.result"
```

초반에는 `.result`가 없을 수 있다. 이때는 `.errors`와 `.output`이 더 중요하다.

| 관찰 | 의미 |
|---|---|
| 컴파일 실패 | 구현 이전 문제다. 테스트 실행 단계까지 못 갔다. |
| 부팅 중 panic | VM init, process init, thread 초기화 경로 문제 가능성이 있다. |
| load 전에 죽음 | `load_segment`, SPT 등록, stack 초기화 의심. |
| page fault에서 panic | `vm_try_handle_fault`, `spt_find_page`, claim 경로 의심. |
| `lazy-anon`의 `initial pages status`까지 출력 | user program 실행은 어느 정도 됐다. |
| `lazy-anon`의 `load pages`까지 출력 | lazy fault 처리 흐름이 일부 동작한다. |
| checker mismatch | 실행은 끝났고, 의미나 출력이 기대와 다르다. |

초반 smoke test는 다음 순서가 좋다.

```bash
make -C "$PINTOS_ROOT/vm" build/tests/vm/lazy-anon.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/pt-bad-addr.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/pt-write-code.result
```

V6까지 뚫린 뒤에는 다음을 추가한다.

```bash
make -C "$PINTOS_ROOT/vm" build/tests/vm/lazy-file.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/pt-grow-stack.result
```

정리하면 초반 검증 기준은 다음이다.

```text
V1~V2: build + invariant 확인
V3~V4: lazy entry가 SPT에 들어가는지 확인
V5: page fault가 SPT lookup/claim까지 가는지 확인
V6: user program이 stack을 쓰고 실행되는지 확인
V7 이후: 실제 PASS 테스트로 확인
```

초반에는 “통과했는가”보다 “죽는 위치가 앞으로 전진했는가”를 본다. 이 진행도를 매일 공유해야 팀 디버깅이 가능하다.

## 현실적인 마일스톤

### M0. 빌드 가능 상태

목표:

- VM 설정을 켠 상태에서 빌드가 된다.
- `vm` 디렉터리의 skeleton TODO를 건드리기 시작해도 컴파일이 깨지지 않는다.

관련 티켓:

- V0 VM Build / Template 연결
- V1 SPT Core 일부
- V2 Frame Claim Minimal 일부

검증:

```bash
make -C "$PINTOS_ROOT/vm"
```

이 단계에서는 VM 테스트 PASS를 기대하지 않는다. 컴파일 성공이 핵심이다.

### M1. 유저 프로그램 실행 최소 복구

목표:

- executable page가 lazy loading으로 등록된다.
- page fault가 SPT를 통해 해당 page를 찾아 frame에 claim한다.
- initial stack이 VM 방식으로 올라온다.
- Project 2 userprog 회귀가 다시 의미 있게 관찰되는 상태가 된다.

관련 티켓:

- V1 Supplemental Page Table Core
- V2 Frame Claim Minimal
- V3 Uninit / Anon Page Minimal
- V4 Executable Lazy Loading
- V5 Page Fault Core
- V6 Initial Stack VM 전환

검증 후보:

```bash
make -C "$PINTOS_ROOT/vm" build/tests/vm/lazy-anon.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/lazy-file.result
```

주의:

- 이 단계 전에는 PASS가 잘 안 나오는 것이 이상하지 않다.
- 대신 kernel panic 위치, fault address, `.output` 진행 메시지를 봐야 한다.

### M2. 첫 VM PASS 목표

목표:

- lazy anonymous page가 실제 접근 전에는 frame을 갖지 않는다.
- file-backed lazy page가 실제 접근 시점에 로드된다.
- read-only page write, kernel address, bad address가 kernel panic이 아니라 정해진 실패 경로로 처리된다.

관련 티켓:

- V3
- V4
- V5
- V10 일부

검증 후보:

```bash
make -C "$PINTOS_ROOT/vm" build/tests/vm/lazy-anon.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/lazy-file.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/pt-bad-addr.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/pt-write-code.result
```

이 단계가 되면 팀이 처음으로 “VM이 최소 동작한다”고 판단할 수 있다.

### M3. Stack Growth 점수 목표

목표:

- 1 page stack 한계를 넘는 정상 stack 접근을 성장시킨다.
- `rsp` 기준 heuristic으로 stack 접근과 잘못된 접근을 구분한다.
- stack 최대 크기 1MB 제한을 적용한다.

관련 티켓:

- V6 Initial Stack VM 전환
- V7 Stack Growth

검증 후보:

```bash
make -C "$PINTOS_ROOT/vm" build/tests/vm/pt-grow-stack.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/pt-grow-stk-sc.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/pt-big-stk-obj.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/pt-grow-bad.result
```

2주 일정에서는 swap보다 stack growth를 먼저 잡는 편이 낫다. 테스트 범위가 작고, fault core 위에 바로 쌓을 수 있다.

### M4. mmap Normal 목표

목표:

- `mmap` syscall validation을 처리한다.
- file-backed page를 lazy하게 등록한다.
- `munmap`에서 dirty page를 write-back한다.
- close/remove 이후 mapping lifetime을 큰 틀에서 맞춘다.

관련 티켓:

- V9 mmap Syscall Entry / Validation
- V10 File-backed Page Core
- V11 mmap Normal / munmap Normal
- V12 일부

검증 후보:

```bash
make -C "$PINTOS_ROOT/vm" build/tests/vm/mmap-read.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/mmap-write.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/mmap-unmap.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/mmap-close.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/mmap-null.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/mmap-misalign.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/mmap-zero-len.result
```

시간이 부족하면 mmap robustness 전체보다 `mmap-read`, `mmap-write`, `mmap-unmap`, `mmap-close`를 먼저 본다.

### M5. Eviction / Swap 후순위 목표

목표:

- frame table에서 victim을 고른다.
- anonymous page를 swap disk로 내보내고 다시 읽는다.
- file-backed page는 file 자체를 backing store로 사용한다.
- memory pressure 테스트에서 데이터가 유지된다.

관련 티켓:

- V13 Frame Table / Eviction Core
- V14 Anonymous Swap
- V15 File-backed Eviction / Swap
- V16 VM Fork / mmap Inherit / Swap Fork 통합

검증 후보:

```bash
make -C "$PINTOS_ROOT/vm" build/tests/vm/swap-anon.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/swap-file.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/swap-iter.result
make -C "$PINTOS_ROOT/vm" build/tests/vm/swap-fork.result
```

2주 일정에서 AI 없이 여기까지 안정화하는 것은 난도가 높다. M1-M4가 흔들리면 swap은 과감히 후순위로 미룬다.

## 2주 일정 제안

### 1-2일차: 공통 구조 고정

목표:

- V0 완료
- V1-A~V1-E 완료
- V2-A~V2-C 완료
- V3-A 설계 완료

검증:

- 빌드 성공
- SPT insert/find 기준 합의
- frame 구조 기준 합의

주의:

- 이 시점에 VM PASS가 없어도 정상이다.
- 대신 컴파일을 자주 확인해야 한다.

### 3-4일차: 첫 실행 관문

목표:

- V2-D~V2-E 완료
- V3-B~V3-F 완료
- V4-C~V4-D 진행
- V5-A~V5-D 진행
- V6-A~V6-C 진행

검증:

- `lazy-anon`, `lazy-file` 시도
- 실패해도 `.output`, `.errors`를 기준으로 fault 위치를 좁힌다.

이 구간이 가장 중요하다. 여기서 M1까지 못 가면 이후 모든 팀원이 디버깅 자료 없이 추측으로 움직이기 쉽다.

### 5-6일차: 첫 PASS 확보

목표:

- M1 완료
- M2 일부 완료
- `lazy-anon` 또는 `lazy-file` 중 하나 이상 PASS 목표

검증:

- `lazy-anon`
- `lazy-file`
- `pt-bad-addr`
- `pt-write-code`

판단:

- 둘 다 실패하면 stack/mmap으로 넘어가지 말고 V1-V5를 더 고친다.
- 하나라도 안정적으로 PASS하면 stack growth를 병렬로 시작한다.

### 7-8일차: stack growth 집중

목표:

- V7 완료
- stack growth 테스트 묶음 확보

검증:

- `pt-grow-stack`
- `pt-grow-stk-sc`
- `pt-big-stk-obj`
- `pt-grow-bad`

판단:

- 이 묶음은 점수 대비 범위가 좋다.
- swap보다 먼저 끝내는 것이 낫다.

### 9-11일차: mmap normal

목표:

- V9 validation
- V10 file-backed core
- V11 normal mmap/munmap

검증:

- `mmap-read`
- `mmap-write`
- `mmap-unmap`
- `mmap-close`
- invalid mmap 일부

판단:

- mmap overlap/robustness 전체를 욕심내기보다 normal 4개를 먼저 고정한다.

### 12-14일차: 선택지 분기

M1-M4가 안정적이면:

- V12 robustness 보강
- V13 eviction 착수
- V14 anonymous swap 일부

M1-M4가 불안정하면:

- swap 착수하지 않는다.
- lazy, stack, mmap normal 회귀를 안정화한다.
- kernel panic, resource leak, dirty write-back 누락을 먼저 잡는다.

## 팀 운영 기준

### 첫 주에는 PASS보다 “실행 가능성”이 중요하다

초반에는 VM PASS가 없을 수 있다. 대신 다음을 매일 확인한다.

- 빌드가 되는가
- kernel panic이 같은 위치에서 나는가
- fault address가 예상 영역인가
- `.output`에서 어느 `msg()`까지 찍혔는가
- `.errors`가 timeout인지 panic인지 checker mismatch인지 구분되는가

### 첫 PASS가 나오기 전에는 작업을 넓히지 않는다

`lazy-anon` 또는 `lazy-file`이 하나도 PASS하지 않는 상태에서 mmap/swap으로 넓히면 디버깅 지점이 폭발한다.

우선순위:

```text
빌드 성공
-> lazy page fault 동작
-> initial stack 동작
-> lazy-anon/lazy-file 첫 PASS
-> stack growth
-> mmap normal
-> swap
```

### swap은 후순위로 둔다

swap은 frame eviction, dirty/accessed bit, anon/file-backed swap operation, process cleanup이 함께 걸린다. 앞 단계가 불안정하면 실패 원인을 분리하기 어렵다.

2주 일정에서 현실적인 후순위는 다음이다.

1. `lazy-*`
2. `pt-grow-*`
3. `mmap-read/write/unmap/close`
4. mmap invalid 일부
5. swap 일부

## 디버깅 산출물 읽는 법

테스트는 팀원이 직접 실행한다.

전체 VM 테스트:

```bash
make -C "$PINTOS_ROOT/vm" check
cat "$PINTOS_ROOT/vm/build/results"
```

특정 테스트:

```bash
make -C "$PINTOS_ROOT/vm" build/tests/vm/TEST_NAME.result
```

확인할 파일:

```text
pintos/vm/build/results
pintos/vm/build/tests/vm/TEST_NAME.output
pintos/vm/build/tests/vm/TEST_NAME.errors
pintos/vm/build/tests/vm/TEST_NAME.result
```

판단 기준:

| 상태 | 의미 | 다음 행동 |
|---|---|---|
| 컴파일 실패 | 아직 테스트 이전 문제 | 최근 변경 파일, header, prototype부터 확인 |
| `.result` 없음 | panic, timeout, interrupt 가능성 | `.errors`, `.output` 먼저 확인 |
| `.output` 일부 있음 | 테스트가 어느 지점까지 진행됐는지 확인 가능 | 마지막 `msg()` 이후 fault path 추적 |
| checker mismatch | 실행은 됐지만 출력/동작이 기대와 다름 | `.ck`와 `.output` 비교 |
| kernel panic | fault handling 또는 kernel invariant 문제 가능성 | panic stack, fault address, current thread 확인 |
| timeout | deadlock, infinite loop, eviction loop 가능성 | lock/sema, wait path, victim selection 확인 |

## 중간 목표별 포기선

2주 안에 다 못 끝낼 가능성이 크므로 포기선을 미리 정한다.

| 날짜 | 최소 도달 목표 | 도달 못 했을 때 |
|---|---|---|
| 4일차 끝 | M1에 가까운 실행 흐름 | mmap/swap 착수 금지, V1-V6 집중 |
| 6일차 끝 | `lazy-anon` 또는 `lazy-file` 첫 PASS | stack growth 착수 보류 |
| 8일차 끝 | stack growth 일부 PASS | mmap normal 범위 축소 |
| 11일차 끝 | mmap normal 일부 PASS | swap 포기, robustness와 cleanup 정리 |
| 14일차 | COW 제외 제출 가능한 안정 상태 | 불안정한 swap 코드는 제출 전 위험도 판단 |

## 최종 권장 목표

AI 없이 2주라면 목표를 세 단계로 잡는다.

필수 목표:

- V1~V6 완료
- `lazy-anon` / `lazy-file` 중 최소 하나 이상 안정화
- Project 2 회귀가 크게 깨지지 않는지 확인

현실적 점수 목표:

- V7 stack growth 완료
- `pt-grow-*` 계열 확보
- V9~V11 mmap normal 일부 확보

도전 목표:

- V12 mmap robustness 확대
- V13~V15 swap 일부
- V16 `swap-fork`, `mmap-inherit` 일부

가장 중요한 판단은 이것이다. 첫 VM PASS가 나오기 전에는 범위를 넓히지 않는다. `lazy-*`와 stack growth가 안정화된 뒤 mmap으로 가고, swap은 마지막에 남은 시간으로 판단한다.
