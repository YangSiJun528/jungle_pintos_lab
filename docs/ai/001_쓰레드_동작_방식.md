# Pintos Thread 동작 방식

이 글은 [Week02 Context Switch 전사본](<../reference/kaist-oslab-pintos-slides-original/scripts/[Week02] Pintos Project Context Switch.md>)을 기준으로, Pintos에서 thread가 만들어지고 CPU를 넘겨받고 다시 내려오는 흐름을 정리한 것이다.

전사본은 전통적인 Pintos 설명에 맞춰 `switch_threads()`, `esp`, `ebx`, `ebp`, `esi`, `edi` 같은 32-bit x86 이름을 사용한다. 현재 저장소의 KAIST Pintos는 x86-64 코드라 실제 구현 이름은 `thread_launch()`, `do_iret()`, `rsp`, `intr_frame` 쪽에 가깝다. 그래도 핵심 원리는 같다. 현재 thread의 실행 문맥을 저장하고, 다음 thread의 저장된 실행 문맥을 CPU에 복원한다.

## 1. Thread는 무엇으로 표현되는가

Pintos에서 thread 또는 process를 대표하는 핵심 자료구조는 `struct thread`다. 전사본은 `struct thread`가 thread id, status, priority, kernel stack pointer, page table pointer 같은 정보를 가진다고 설명한다.

현재 저장소에서는 [pintos/include/threads/thread.h](../../pintos/include/threads/thread.h)에 `struct thread`가 정의되어 있다. 중요한 필드는 다음처럼 보면 된다.

- `tid`: thread identifier
- `status`: 현재 thread 상태
- `name`: 디버깅용 이름
- `priority`: scheduling에 쓰는 우선순위
- `elem`: ready list나 wait list에 들어갈 때 쓰는 list element
- `pml4`: user process의 page table 정보
- `tf`: context switch에 필요한 register frame
- `magic`: kernel stack overflow 감지용 값

Pintos의 각 thread는 보통 자기 4 KB page 하나를 가진다. 페이지 아래쪽에는 `struct thread`가 있고, 나머지 위쪽 공간은 kernel stack으로 쓴다. kernel stack은 높은 주소에서 낮은 주소 방향으로 자란다. 그래서 `struct thread`가 너무 커지거나 kernel stack을 너무 많이 쓰면 서로 침범할 수 있다.

## 2. Thread 상태

전사본은 Pintos thread 상태를 네 가지로 설명한다.

- `THREAD_RUNNING`: 지금 CPU에서 실행 중인 thread
- `THREAD_READY`: 실행 준비가 끝났고 CPU만 기다리는 thread
- `THREAD_BLOCKED`: 어떤 이벤트를 기다리느라 실행될 수 없는 thread
- `THREAD_DYING`: 종료를 요청했고, 커널이 자료구조를 완전히 정리하기 전 상태

중요한 점은 `schedule()`이 호출되기 전에 현재 thread 상태가 `THREAD_RUNNING`이 아닌 다른 상태로 바뀌어야 한다는 것이다. 예를 들어 block이면 `THREAD_BLOCKED`, yield면 `THREAD_READY`, exit이면 `THREAD_DYING`이 된다.

## 3. Ready List와 All List

전사본은 Pintos에 두 종류의 thread list가 있다고 설명한다.

- ready list: CPU를 받을 준비가 된 thread들의 목록
- all list: 시스템에 존재하는 모든 thread들의 목록

강의 흐름에서는 새 thread가 만들어지면 먼저 all list에 들어가고, 실행 준비가 되면 ready list에 들어간다. ready list에 있다는 것은 "지금 실행 중은 아니지만, scheduler가 고르면 바로 실행할 수 있다"는 뜻이다.

현재 저장소의 `thread.c`에서는 `ready_list`가 핵심 run queue 역할을 한다. `thread_unblock()`은 blocked thread를 ready 상태로 바꾸고 `ready_list` 뒤에 넣는다. `thread_yield()`도 현재 thread를 다시 실행 가능한 상태로 만들 때 `ready_list` 뒤에 넣는다.

## 4. Thread 생성 흐름

`thread_create(name, priority, function, aux)`는 새 thread를 만든다. 전사본 기준의 큰 흐름은 다음과 같다.

1. 새 `struct thread`와 kernel stack으로 쓸 page를 준비한다.
2. `init_thread()`로 기본 필드를 초기화한다.
3. 새 thread의 초기 상태를 blocked로 둔다.
4. thread id, priority, stack, 실행할 함수 정보를 채운다.
5. 실행 준비가 끝나면 ready list에 넣고 상태를 ready로 바꾼다.

현재 저장소의 `thread_create()`도 비슷하다. `palloc_get_page(PAL_ZERO)`로 page를 받고, `init_thread()`로 `struct thread`를 초기화한 뒤, 새 thread가 처음 실행할 위치를 `kernel_thread`로 맞춘다. 그리고 `thread_unblock(t)`를 호출해 ready queue에 넣는다.

여기서 중요한 점은 thread를 만들었다고 바로 CPU에서 실행되는 것은 아니라는 것이다. 새 thread는 ready list에 들어간다. 실제 실행 여부는 scheduler가 언제 그 thread를 고르느냐에 달려 있다.

## 5. CPU를 내려놓는 세 가지 이유

전사본은 `schedule()`이 호출되는 대표 상황을 세 가지로 정리한다.

1. exit: 현재 thread가 종료한다.
2. block: 현재 thread가 I/O나 synchronization event를 기다린다.
3. yield: 현재 thread가 자발적으로 CPU를 양보한다.

이 세 경우 모두 공통점이 있다. 현재 running thread가 계속 running 상태로 있을 수 없으므로, 상태를 먼저 바꾼 뒤 `schedule()`을 호출한다.

`thread_block()` 흐름은 다음과 같다.

1. interrupt가 꺼져 있는지 확인한다.
2. 현재 thread 상태를 `THREAD_BLOCKED`로 바꾼다.
3. `schedule()`을 호출한다.

`thread_yield()` 흐름은 다음과 같다.

1. interrupt를 끈다.
2. idle thread가 아니라면 현재 thread를 ready list 뒤에 넣는다.
3. 현재 thread 상태를 `THREAD_READY`로 바꾼다.
4. `schedule()`을 호출한다.

`thread_exit()` 흐름은 다음과 같다.

1. user process 정리가 필요하면 먼저 처리한다.
2. interrupt를 끈다.
3. 현재 thread 상태를 `THREAD_DYING`으로 바꾼다.
4. `schedule()`을 호출한다.
5. 종료한 thread는 다시 돌아오지 않는다.

## 6. `schedule()`의 역할

`schedule()`의 목적은 단순하다. 지금 실행 중이던 thread를 내려놓고, 다음에 실행할 thread를 CPU에 올린다.

전사본 기준 흐름은 다음과 같다.

1. 현재 thread 포인터를 얻는다.
2. `next_thread_to_run()`으로 다음 thread를 고른다.
3. 현재 thread와 다음 thread가 다르면 context switch를 수행한다.
4. 전환 뒤 `thread_schedule_tail()`에서 새 thread 상태를 running으로 만들고, 이전 thread가 dying이면 정리한다.

현재 저장소 흐름도 같은 구조다.

1. `schedule()`이 `running_thread()`로 현재 thread를 얻는다.
2. `next_thread_to_run()`이 ready list에서 다음 thread를 꺼낸다.
3. 다음 thread의 상태를 `THREAD_RUNNING`으로 바꾼다.
4. time slice를 초기화한다.
5. user process라면 주소 공간을 activate한다.
6. 현재 thread와 다음 thread가 다르면 `thread_launch(next)`로 실제 전환을 한다.

ready list가 비어 있으면 `next_thread_to_run()`은 idle thread를 반환한다. idle thread는 할 일이 없을 때 CPU가 멈춰서 다음 interrupt를 기다리게 하는 특수 thread다.

## 7. Context란 무엇인가

context는 thread가 나중에 다시 실행되기 위해 필요한 CPU 상태다. 최소한 다음 정보가 필요하다.

- instruction pointer: 다음에 실행할 명령 위치
- stack pointer: 현재 stack top 위치
- general-purpose registers: 계산 중이던 값들
- segment, flags, interrupt 관련 상태
- user process라면 page table 같은 주소 공간 정보

전사본은 이를 "현재 context를 저장하고 다음 context를 복원한다"고 설명한다. 현재 thread가 다시 선택되었을 때, CPU register와 stack pointer가 이전 값으로 돌아가면 thread는 자기가 멈췄던 바로 그 지점에서 이어서 실행되는 것처럼 보인다.

## 8. Stack이 중요한 이유

context switch 설명에서 stack이 핵심인 이유는 함수 호출, local variable, return address, 일부 register 저장이 모두 stack과 관련되기 때문이다.

Pintos에는 user stack과 kernel stack이 있다.

- user stack: user mode에서 함수 호출과 local variable을 위해 사용
- kernel stack: kernel mode에서 system call, interrupt, scheduler, synchronization 코드가 실행될 때 사용

thread가 kernel 안에서 block되거나 yield하면, scheduler와 context switch 코드는 그 thread의 kernel stack 위에서 실행된다. 따라서 현재 kernel stack top을 저장해 두면, 나중에 해당 thread를 다시 실행할 때 같은 kernel stack 위치로 돌아갈 수 있다.

## 9. Context Switch의 네 단계

전사본은 `switch_threads(cur, next)`를 네 단계로 설명한다.

1. 현재 CPU register들을 현재 thread의 kernel stack에 저장한다.
2. 현재 stack top 주소를 현재 `struct thread`에 저장한다.
3. CPU stack pointer를 다음 thread의 저장된 stack top으로 바꾼다.
4. 다음 thread의 stack에서 register들을 꺼내 CPU에 복원한다.

이 과정을 끝내면 CPU는 같은 CPU지만, stack pointer와 register 값은 다음 thread의 것이 된다. 그래서 이후 실행은 다음 thread가 이어받는다.

현재 저장소의 x86-64 구현은 형태가 조금 다르다. `thread_launch(next)`가 현재 register들을 현재 thread의 `intr_frame`에 저장하고, `do_iret()`가 다음 thread의 `intr_frame`을 기준으로 register와 `rsp`, `rip`을 복원한다. 강의의 `switch_threads()`가 stack pointer 중심으로 설명된다면, 현재 코드는 `intr_frame` 중심으로 같은 문제를 해결한다고 보면 된다.

## 10. Voluntary Switch와 Preemption

전사본은 기본 Pintos의 context switch를 주로 voluntary release 관점에서 설명한다. 즉 현재 thread가 `exit`, `block`, `yield` 같은 행동을 통해 스스로 CPU를 내려놓는다.

반대로 involuntary release는 현재 thread 의사와 상관없이 CPU를 빼앗기는 경우다. 예를 들면 더 높은 priority thread가 도착했거나 time quantum이 끝났을 때다.

현재 저장소의 기본 코드에는 timer tick마다 `thread_tick()`이 호출되고, `TIME_SLICE`만큼 tick이 지나면 `intr_yield_on_return()`으로 interrupt handler가 끝난 뒤 yield가 일어나도록 한다. Project1에서는 여기에 priority scheduling을 추가하면서, ready list에 더 높은 priority thread가 들어왔을 때 현재 thread가 CPU를 양보하도록 바꾸게 된다.

## 11. 한 번에 보는 실행 흐름

새 thread가 만들어져 실행되고 다시 내려오는 흐름은 다음처럼 볼 수 있다.

1. `thread_create()`가 새 `struct thread`와 kernel stack을 준비한다.
2. 새 thread는 `THREAD_BLOCKED`로 초기화된다.
3. 실행 시작 정보가 thread context에 기록된다.
4. `thread_unblock()`이 새 thread를 `THREAD_READY`로 바꾸고 ready list에 넣는다.
5. 현재 thread가 yield, block, exit하거나 timer/preemption 조건이 생긴다.
6. 현재 thread 상태가 ready, blocked, dying 중 하나로 바뀐다.
7. `schedule()`이 ready list에서 다음 thread를 고른다.
8. context switch가 현재 context를 저장하고 다음 context를 복원한다.
9. 다음 thread가 `THREAD_RUNNING` 상태로 CPU에서 실행된다.
10. 이전 thread가 dying이면 나중에 page가 정리된다.

핵심은 "thread가 CPU를 가진다"는 말이 실제로는 CPU register와 stack pointer가 그 thread의 저장된 context를 가리킨다는 뜻이라는 점이다. scheduler는 다음에 실행할 `struct thread`를 고르고, context switch 코드는 CPU 상태를 그 thread의 상태로 갈아끼운다.

## 핵심 정리

Pintos thread 동작은 세 가지 축으로 이해하면 된다.

첫째, `struct thread`는 thread의 신분증이자 실행 상태 저장소다. id, status, priority, list element, address space, context 정보가 여기에 묶인다.

둘째, scheduler는 ready list에서 다음 thread를 고른다. running thread가 block, yield, exit 또는 preemption 조건 때문에 CPU를 내려놓으면 `schedule()`이 다음 thread를 선택한다.

셋째, context switch는 CPU를 실제로 넘겨주는 낮은 수준의 작업이다. 현재 thread의 register와 stack 상태를 저장하고, 다음 thread의 register와 stack 상태를 복원한다. 이 복원 덕분에 각 thread는 자신이 멈춘 지점에서 계속 실행되는 것처럼 보인다.
