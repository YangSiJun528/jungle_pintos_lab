# VM 메모리 구조: kernel view와 user view가 갈라지는 방식

이 글의 출발점은 단순하다.

> VM에서 kernel memory는 왜 계속 같은데, user memory는 process마다 달라 보일까?

여기서 VM은 “RAM을 크게 보이게 하는 기술” 정도로만 보면 계속 헷갈린다. 더 정확한 mental model은 이쪽에 가깝다.

```text
주소 이름        ->  번역 규칙        ->  실제 byte
virtual address ->  page table       ->  physical frame
```

kernel과 user의 차이는 이 번역 규칙이 어디에서 고정되고, 어디에서 process별로 바뀌는지에서 나온다. Pintos 기준으로는 세 가지를 먼저 분리해야 한다.

- **kernel virtual address space**: 모든 process에서 같은 kernel view
- **user virtual address space**: process마다 달라지는 user view
- **physical memory**: 실제 byte가 들어 있는 RAM frame

그리고 이 셋을 연결하는 장치가 page table, MMU, TLB, supplemental page table, frame table, swap metadata다.

이 글의 중심은 Pintos의 VM 구조다. 특히 일반적인 page table 설명만으로는 잘 드러나지 않는 **kernel direct map**을 별도 축으로 유지한다. Pintos에서 kernel/user memory 관계를 이해하려면 direct map이 빠지면 안 된다.

## 1. 한 장 mental model

Pintos VM을 한 장으로 줄이면 이렇게 볼 수 있다.

```text
                         active PML4
user VA 0x500000  ---------------------------->  physical frame F
   process별 이름                                  실제 byte
        |                                             ^
        |                                             |
        |                                             |
        +-- Process A에서는 frame A                  |
        +-- Process B에서는 frame B                  |
        +-- Process C에서는 no frame                 |
                                                      |
kernel VA KERN_BASE + paddr  ------------------------+
        모든 process에서 같은 kernel-side alias
```

중요한 포인트는 두 가지다.

첫째, **user VA는 process별 page table을 통해 해석된다.** 같은 `0x500000`이라도 Process A와 Process B에서 다른 physical frame을 볼 수 있다.

둘째, **kernel direct map은 physical RAM을 kernel VA로 보는 전역 alias다.** frame이 user page에 붙어 있든 kernel metadata에 쓰이든, RAM에 올라와 있는 frame이라면 kernel은 direct-map 주소로 그 byte를 볼 수 있다.

이 둘이 동시에 존재하기 때문에 하나의 physical frame은 이렇게 두 이름을 가질 수 있다.

```text
physical frame F
  ├─ user VA:   process의 page table에 등록된 upage
  └─ kernel VA: KERN_BASE + physical address
```

복사본이 둘이라는 뜻은 아니다. 이름이 둘이고, byte 저장소는 하나다.

## 2. VM을 보는 네 가지 층

VM을 이해할 때 한 층만 보면 설명이 자꾸 뒤섞인다. 다음 네 층을 분리해 두면 덜 헷갈린다.

| 층 | 질문 | Pintos에서 보이는 것 |
| --- | --- | --- |
| 주소 이름 | 누가 어떤 주소를 사용하나? | user VA, kernel VA, `KERN_BASE` |
| 번역 규칙 | 이 주소가 어느 frame으로 가나? | PML4, PTE, TLB |
| 실제 byte | 지금 RAM 어디에 내용이 있나? | physical frame, user pool frame |
| 장부 | frame이 없으면 어디서 복구하나? | SPT, frame table, bitmap, swap metadata |

CPU/MMU는 주로 두 번째 층, 즉 주소 번역과 permission check를 담당한다. OS는 네 번째 층, 즉 page의 정체성과 backing store를 관리한다. physical frame은 세 번째 층이다. 실제 code/data/stack byte가 들어 있는 곳은 결국 frame이다.

여기서 자주 생기는 오해가 있다.

> page table에 주소 범위가 보이면 실제 RAM도 이미 있는 것 아닌가?

아니다. page table entry가 present가 아니거나, supplemental page table에 lazy page metadata만 있으면 아직 RAM frame이 붙지 않았을 수 있다. VM에서는 “주소로 표현 가능”과 “현재 RAM에 resident”가 분리된다.

## 3. Kernel 영역: process가 바뀌어도 유지되는 전역 view

Pintos의 virtual memory는 `KERN_BASE`를 기준으로 갈라진다.

```text
0                         KERN_BASE
|-------------------------|-----------------------------|
 user virtual memory       kernel virtual memory
 process별                 전역
```

user virtual memory는 process마다 다르다. 반대로 kernel virtual memory는 global이다. 어떤 user process나 kernel thread가 실행 중이든 kernel virtual address는 같은 방식으로 매핑된다.

kernel 영역에는 보통 이런 것들이 들어간다.

- kernel code
- kernel initialized data / BSS
- kernel stack
- thread page
- page table memory
- allocator metadata
- bitmap
- frame table
- filesystem buffer 같은 kernel object

여기서 핵심은 “kernel 영역이 전역”이라는 말의 의미다. 전역이라는 말은 모든 process가 kernel memory를 user mode에서 마음대로 볼 수 있다는 뜻이 아니다. user process는 `KERN_BASE` 위 주소에 접근할 수 없다. MMU의 user/supervisor permission이 이를 막고, 잘못 접근하면 page fault로 이어진다.

전역이라는 말은 이쪽에 가깝다.

```text
Process A active PML4:
  user mappings A
  same kernel mappings

Process B active PML4:
  user mappings B
  same kernel mappings
```

process switch 때 user mapping은 바뀌지만 kernel mapping은 같은 위치에 남는다. 그래서 kernel code는 process가 바뀌어도 자기 code, data, allocator, frame metadata를 같은 VA로 계속 접근할 수 있다.

구현 관점에서 보면 “같은 kernel mapping”은 막연한 비유가 아니다. Pintos는 새 process용 PML4를 만들 때 kernel mapping이 들어 있는 `base_pml4`를 복사한다. 그 뒤 user code, data, stack, lazy page 같은 process별 mapping을 user 영역에 추가한다. 따라서 각 process의 PML4 root는 서로 다르지만, kernel-side entry들은 같은 kernel address layout을 가리키는 공통 기반을 가진다.

```text
pml4_create()
  -> new PML4 root
  -> copy base_pml4
  -> user entries are filled per process
  -> kernel entries start from the shared kernel layout
```

그래서 kernel 영역이 “전역”이라는 말은 하나의 process PML4만 쓴다는 뜻이 아니다. process별 PML4 안에 kernel을 보기 위한 같은 entry들이 들어 있고, CPU가 어느 process PML4를 active로 쓰더라도 kernel VA는 같은 의미를 유지한다는 뜻이다.

## 4. Kernel Direct Map: physical RAM을 보는 커널의 alias 창

Pintos에서 kernel virtual memory는 physical memory에 one-to-one으로 매핑된다. 이 구조가 direct map이다.

```text
kernel virtual address = KERN_BASE + physical address
physical address       = kernel virtual address - KERN_BASE
```

예를 들어 physical address `0x1234`에 있는 byte는 kernel VA `KERN_BASE + 0x1234`로 볼 수 있다. 이 mapping은 machine의 physical memory 크기까지 이어진다.

여기서 “1:1로 들고 있다”는 말을 조심해야 한다. direct map은 RAM을 한 번 더 복사해서 kernel이 소유한다는 뜻이 아니다. 같은 physical frame을 kernel VA로도 볼 수 있게 만든 alias다.

```text
physical frame F
  byte storage: 실제 RAM

kernel direct-map VA
  KERN_BASE + F의 physical address
  -> frame F의 같은 byte를 봄
```

direct map이 필요한 이유는 현실적이다. x86-64는 physical address를 pointer처럼 직접 dereference하는 모델이 아니다. kernel도 C 코드에서 pointer로 memory를 읽고 써야 한다. 그래서 physical frame을 다루려면 kernel virtual address가 필요하다.

Pintos boot 초기화도 이 관점으로 보면 단순하다. kernel은 초기 paging 설정에서 physical address range를 `KERN_BASE + paddr` 형태의 kernel VA range에 mapping한다. Linux x86-64 문서의 direct mapping도 같은 계열의 아이디어다. Linux에서는 direct mapping 영역이 system의 highest memory address까지 덮고, 경우에 따라 PCI memory hole 같은 빈 physical address 구간도 alias window 안에 포함될 수 있다.

Pintos 설명에 이 Linux 주소 layout을 그대로 가져오면 안 되지만, 개념상 중요한 결론은 같다.

```text
direct map은 "사용 중인 user frame 목록"만 보는 창이 아니다.
direct map은 physical address space를 kernel VA로 부르는 창이다.
```

그래서 시각화에서 direct-map window는 user pool, kernel pool, kernel image 같은 하위 구간을 나눠 보여 줄 수 있지만, 더 크게는 `KERN_BASE + paddr` 방식의 하나의 alias range로 묶여야 한다.

Pintos의 `pml4_set_page(pml4, upage, kpage, rw)`를 볼 때 `kpage`가 이 관점에서 중요하다. `kpage`는 user process가 보는 주소가 아니다. kernel이 user pool frame을 접근하기 위해 가진 kernel virtual address다. mapping의 의미는 이렇다.

```text
upage  ->  kpage가 식별하는 physical frame
```

즉 kernel은 먼저 frame을 kernel VA로 채우고, 그 frame을 user VA에 연결한다.

```text
1. user pool에서 frame F 확보
2. kernel direct-map VA로 frame F byte 초기화
3. process PML4에 upage -> frame F 등록
4. user process는 upage로 같은 byte 접근
```

direct map은 일반적인 page table 설명만으로는 잘 드러나지 않는다. 하지만 Pintos에서는 kernel이 frame byte를 직접 만지는 경로를 이해하는 핵심 연결고리다.

## 5. User 영역: process마다 바뀌는 per-process view

user virtual memory는 `0`부터 `KERN_BASE` 아래까지다. 각 process는 자기 user address space를 가진다. 같은 user VA라도 process마다 다른 의미가 될 수 있다.

```text
Process A:
  user VA 0x500000 -> physical frame A

Process B:
  user VA 0x500000 -> physical frame B

Process C:
  user VA 0x500000 -> no frame yet
```

여기서 바뀌는 것은 user pool 자체가 아니다. user pool은 전역 physical RAM의 일부다. 바뀌는 것은 CPU가 현재 사용하는 page table, 즉 active PML4다.

```text
same user VA
  + active PML4 A -> frame A
  + active PML4 B -> frame B
  + active PML4 C -> not-present
```

이 구조 덕분에 process는 “나만의 연속된 주소 공간”을 가진 것처럼 실행된다. 실제 RAM은 전역 자원이고, OS가 page table을 바꿔 각 process에게 다른 view를 보여 줄 뿐이다.

thread까지 같이 보면 기준이 더 명확해진다.

- 같은 process 안의 thread: 같은 user address space 공유
- 다른 process의 thread: 다른 user address space 사용
- kernel virtual mapping: 둘 다 같은 전역 mapping 사용
- thread page/kernel stack: thread별 kernel memory

Pintos Project 2 기준 user process는 하나의 thread를 갖지만, VM 구조를 이해할 때는 “thread가 어떤 process의 address space를 보느냐”가 더 중요한 질문이다.

## 6. Active PML4: user view가 바뀌는 지점

CPU는 memory access를 할 때 active page table을 기준으로 virtual address를 번역한다. x86-64에서 CR3는 최상위 page translation table의 base를 가리키고, Pintos가 쓰는 4-level paging에서는 그 최상위가 PML4다.

PML4는 table이지만, 단순 보관용 table은 아니다. CPU/MMU가 현재 virtual address를 physical frame으로 번역할 때 실제로 따라가는 active root다. 그래서 같은 `0x500000`이라는 user VA도 active PML4가 무엇인지에 따라 다른 frame으로 번역될 수 있다.

역할을 나누면 이렇다.

```text
kernel:
  process별 PML4/page table을 만들고 mapping을 설치한다.

CPU/MMU:
  현재 active PML4를 따라 VA -> physical frame translation을 수행한다.

page fault handler:
  translation 실패나 permission violation이 났을 때 개입한다.
```

즉 매 memory access마다 kernel이 직접 주소를 번역하는 것이 아니다. kernel은 page table을 구성하고, context switch 때 `pml4_activate()`로 active PML4를 바꾸며, page fault가 났을 때 복구하거나 process를 종료한다. 정상적인 load/store의 주소 번역은 CPU/MMU가 active PML4와 TLB를 사용해서 처리한다.

x86-64 long mode에서는 모든 64-bit 값이 곧바로 유효한 virtual address가 되는 것이 아니다. 일반적인 4-level paging에서는 address bit 일부가 canonical form을 만족해야 하고, 나머지 bit가 PML4/PDP/PD/PT index와 page offset으로 쓰인다. Pintos의 `KERN_BASE = 0x8004000000`은 Pintos가 정한 user/kernel 경계이지, Linux의 higher-half kernel layout이나 canonical hole 배치를 그대로 따른 값은 아니다.

page table entry가 담는 주소도 중요하다. page walk에서 상위 entry는 다음 level table의 physical frame을 가리키고, 마지막 PTE는 data page의 physical frame을 가리킨다. CPU/MMU는 이 physical frame 번호와 page offset을 합쳐 최종 physical address를 만든다.

```text
virtual address
  -> PML4 index
  -> PDP index
  -> PD index
  -> PT index
  -> page offset

PTE target
  -> physical frame number
  -> physical frame number + offset
```

그런데 kernel C code는 physical address를 그대로 pointer처럼 dereference하지 않는다. kernel이 page table page나 user frame을 초기화해야 할 때는 그 physical frame에 대응하는 kernel VA, 즉 direct-map alias를 통해 접근한다. 그래서 active PML4 설명과 direct map 설명은 분리되어 있지만 실제 구현에서는 맞물린다.

context switch가 일어나면 register와 stack만 바뀌는 게 아니다. CPU가 앞으로 어떤 page table로 user VA를 해석할지도 바뀐다.

```text
current thread/process
  -> struct thread 안의 pml4
  -> pml4_activate()
  -> CPU active page table 변경
  -> user VA 해석 변경
```

flat page table과 비교하면 PML4의 역할이 더 분명해진다. 모든 virtual page마다 entry를 하나씩 가진 거대한 linear table을 만들면 큰 64-bit address space에서 page table 자체가 너무 커진다. multi-level page table은 필요한 하위 table만 따라 내려가게 해서 이 낭비를 줄인다. 그래서 PML4는 “page 관리를 효율적으로 하기 위한 하드웨어 형식”이면서, 동시에 현재 process의 user VA 해석을 실제로 결정하는 active root이다.

## 7. Physical memory와 user pool

physical memory는 실제 byte가 들어 있는 곳이다. page-size 단위로 보면 physical frame들의 집합이다.

Pintos page allocator는 physical memory를 크게 두 pool로 나눈다.

- kernel pool
- user pool

user pool은 user page용 frame의 출처다. `PAL_USER` flag가 붙은 allocation은 user pool에서 page를 얻는다. Project 3 VM에서는 user space page frame을 user pool에서 얻어야 한다.

여기서 중요한 표현 하나.

> “모든 process의 user pool”이 아니라, “모든 process가 경쟁하는 하나의 user pool”

Process A와 Process B가 각각 user page를 갖더라도 user pool이 process별로 복제되는 것은 아니다. 하나의 전역 physical RAM 자원에서 frame을 나눠 받는다.

```text
global user pool
  frame A -> Process A의 user page
  frame B -> Process B의 user page
  frame C -> free
  frame D -> evict 후보
```

frame byte는 초록색으로 봐도 되는 실제 data다. user code, data, BSS, stack 내용이 들어간다. 반대로 bitmap, frame table, supplemental page table은 frame 내용 자체가 아니라 그 frame의 사용 상태와 연결 관계를 설명하는 metadata다.

## 8. Metadata: VM이 page의 정체성을 기억하는 방식

page table은 중요하지만 page table만으로 VM 전체를 관리하기엔 부족하다.

page table은 CPU/MMU가 바로 번역할 수 있는 mapping을 담는다. 하지만 “이 user page는 원래 어느 file의 어느 offset에서 왔는가”, “지금 swap slot에 나가 있는가”, “lazy load를 기다리는가” 같은 정보는 page table entry만으로 충분히 표현하기 어렵다.

따라서 page table/PML4는 “현재 hardware translation에 필요한 최소 mapping”에 가깝고, supplemental page table은 “그 page가 무엇이며 없을 때 어떻게 복구할지”를 기억하는 OS-side metadata에 가깝다. page table이 비어 있거나 not-present여도 SPT에 lazy/file/swap 정보가 있으면 valid fault로 복구될 수 있다. 반대로 `KERN_BASE` 위 kernel address를 user mode가 건드리는 경우처럼 permission 자체가 틀린 접근은 복구 대상이 아니라 종료 대상이다.

그래서 Pintos Project 3는 supplemental page table을 요구한다.

metadata를 역할별로 나누면 이렇게 정리된다.

| metadata | 기억하는 것 |
| --- | --- |
| page table / PML4 | CPU가 쓸 `VA -> frame` mapping |
| supplemental page table | user page의 정체성, type, backing 정보 |
| frame table | frame이 어떤 page에 붙어 있는지 |
| user pool bitmap | frame free/used 상태 |
| swap table / bitmap | swap slot 사용 상태 |
| file-backed metadata | file, offset, read bytes, zero bytes |
| PTE bits | present, writable, accessed, dirty 등 |

metadata도 memory에 저장되는 byte다. 다만 user page의 code/data/stack byte는 아니다. metadata는 kernel이 VM을 운영하기 위한 장부다.

이 구분이 6번 시각화에서 말한 초록/주황 구분이다.

- 초록: 현재 실제 page byte가 frame에 있음
- 주황: mapping 상태, 예약 상태, backing 위치, 교체 판단 정보

## 9. Memory access fast path: 이미 RAM에 있을 때

page가 이미 RAM에 있고 TLB에도 translation이 있으면 가장 빠른 길을 탄다.

```text
1. CPU가 user VA 생성
2. MMU가 VPN과 offset 분리
3. TLB lookup
4. TLB hit
5. physical frame number + offset
6. cache/RAM 접근
```

TLB hit가 나면 CPU는 매번 PML4부터 PT까지 걸어 내려가지 않아도 된다. TLB는 page byte를 들고 있는 cache가 아니라, 최근의 `virtual page -> physical frame` translation을 들고 있는 작은 hardware cache다.

반대로 page table entry를 바꿨는데 TLB가 예전 translation을 계속 들고 있으면 CPU가 낡은 mapping을 쓸 수 있다. 그래서 kernel은 active page table의 mapping이나 permission bit를 바꾼 뒤 해당 translation을 invalidate해야 한다. Pintos의 `pml4_clear_page()`, `pml4_set_dirty()`, `pml4_set_accessed()`도 현재 active PML4에 대한 변경이면 `invlpg`로 해당 virtual page의 TLB entry를 지운다.

이때 direct map이 필수 단계로 등장하는 것은 아니다. user code가 user VA로 memory를 접근하면 MMU는 active PML4/TLB를 기준으로 physical frame을 찾는다.

direct map은 kernel이 frame을 직접 다룰 때 중요해진다.

```text
user access:
  user VA -> active PML4/TLB -> physical frame

kernel frame access:
  kernel direct-map VA -> physical frame
```

MMU는 permission도 같이 확인한다. user mode에서 supervisor-only page에 접근하려 하거나, read-only page에 write하려 하거나, not-present page를 접근하면 page fault가 난다.

PTE field 관점에서는 다음 bit들이 중요하다.

- present/valid bit: 현재 mapping이 유효한지
- writable/read-only bit: write 가능 여부
- user/supervisor bit: user mode 접근 가능 여부
- accessed bit: 최근 접근 여부
- dirty bit: write로 수정 여부
- global bit: address space 전환에도 유지할 수 있는 공통 mapping

또 accessed/dirty bit와 alias 문제를 같이 봐야 한다. 같은 physical frame을 user VA와 kernel direct-map VA 양쪽으로 볼 수 있으면, 어떤 alias로 접근했는지에 따라 bit 관찰이 달라질 수 있다.

## 10. Page fault path: user VA가 frame을 못 찾을 때

page fault는 “무조건 잘못된 접근”이 아니다. VM에서는 정상적인 lazy loading이나 swap-in의 시작점일 수도 있다.

흐름은 이렇게 갈라진다.

```text
CPU user VA access
  -> MMU/TLB lookup
  -> page table walk
  -> PTE not-present or permission violation
  -> page fault exception
  -> kernel page_fault()
  -> VM fault handler
```

fault가 발생하면 CPU는 faulting virtual address를 CR2에 남기고, error code로 fault의 성격을 알려 준다. Pintos도 `page_fault()`에서 CR2를 읽고, `PF_P`, `PF_W`, `PF_U` bit로 not-present인지 protection violation인지, write인지 read인지, user access인지 kernel access인지 구분한다.

이후 OS가 판단한다.

- 정말 invalid access인가?
- lazy page라서 아직 load만 안 된 상태인가?
- stack growth로 인정할 수 있는가?
- swap-out된 anonymous page인가?
- file-backed page를 다시 읽어야 하는가?
- write-protected page인가?

valid fault라면 kernel은 page를 현실화한다. invalid fault라면 process를 종료해야 한다.

```text
valid fault:
  metadata lookup
  frame allocation
  page content load
  page table update
  instruction retry

invalid fault:
  process termination
  resource cleanup
```

MMU가 disk에서 page를 읽어 오는 것이 아니다. MMU는 실패를 감지하고 fault 정보를 남긴다. 그 다음 판단과 복구는 OS가 맡는다.

## 11. Fault 처리에서 direct map이 쓰이는 위치

page fault를 복구할 때 direct map은 작업용 kernel address로 등장한다.

예를 들어 lazy-loaded executable page에 처음 접근했다고 해보자.

```text
1. user VA 접근
2. page fault 발생
3. SPT에서 "이 page는 file의 이 offset에서 온다" 확인
4. user pool에서 frame F 확보
5. kernel direct-map VA로 frame F에 접근
6. file에서 byte를 읽어 frame F에 채움
7. page table에 upage -> frame F 등록
8. fault 난 instruction 재시도
```

여기서 5번이 direct map의 자리다. kernel은 physical frame F를 직접 숫자 physical address로 dereference하지 않는다. frame F에 대응되는 kernel virtual address로 접근한다.

```text
frame F
  <- kernel writes through KERN_BASE + paddr(F)
  <- user reads through upage after mapping
```

`pml4_set_page()`의 `kpage`도 이 흐름에서 이해하면 자연스럽다. `kpage`는 frame F를 가리키는 kernel VA이고, `upage`는 user process가 사용할 user VA다. function은 둘을 같은 physical frame으로 연결한다.

## 12. Eviction과 swap: direct map의 의미가 바뀌는 순간

direct map은 “현재 physical frame에 들어 있는 byte”를 보여 주는 창이다. 특정 user page의 영원한 이름이 아니다.

eviction이 일어나면 이 차이가 중요해진다.

```text
처음 상태:
  Process A upage 0x500000 -> frame F
  kernel direct VA for F   -> Process A page byte

eviction:
  page byte를 swap/file에 기록
  Process A PTE not-present
  frame F는 free 또는 다른 page에 재사용

이후:
  kernel direct VA for F -> 더 이상 Process A page가 아닐 수 있음
```

page의 정체성은 frame F에 묶여 있지 않다. frame F는 물리 자원이고, page identity는 SPT 같은 metadata에 남는다.

나중에 Process A가 같은 upage를 다시 접근하면 page fault가 난다.

```text
page-in:
  SPT에서 backing 위치 확인
  새 frame G 확보
  swap/file/zero에서 content 복구
  upage -> frame G mapping 등록
```

이제 Process A의 page는 frame G에 있을 수 있다. direct map으로 보면 `KERN_BASE + paddr(G)`가 그 page byte를 보여 준다.

정리하면 이렇다.

> direct map은 page identity가 아니라 physical frame의 현재 내용을 보여 준다.

## 13. CPU 제한과 OS/Pintos 제한

CPU가 표현할 수 있는 virtual address 범위는 매우 크다. x86-64 page table 구조는 virtual address를 여러 index와 offset으로 쪼개서 translation한다. page size가 4 KiB이면 page offset은 12 bit다.

하지만 “CPU가 표현할 수 있다”와 “OS가 실제 frame을 줄 수 있다”는 다르다.

Pintos에서는 user virtual address가 `0`부터 `KERN_BASE` 아래까지다. 현재 KAIST Pintos 코드에서 `KERN_BASE`는 `0x8004000000`이므로, user process가 사용할 수 있는 주소 이름의 상한은 그 직전까지다. 하지만 이 범위 전체가 곧바로 접근 가능한 memory라는 뜻은 아니다.

```text
주소가 user range인가?
  VA < KERN_BASE

지금 접근 가능한가?
  active PML4에 present mapping이 있거나,
  page fault handler가 SPT/backing 정보를 보고 복구할 수 있어야 함
```

Pintos에서 실제 사용 가능한 memory는 이런 것들에 묶인다.

- machine physical memory 크기
- kernel pool / user pool 분할
- user pool bitmap 상태
- 현재 만든 page table mapping 수
- frame table 상태
- swap/file-backed page 정책
- project에서 구현한 VM 기능 범위

direct map도 CPU virtual address 전체를 다 쓰는 개념이 아니다. Pintos가 실제로 direct-map하는 것은 machine의 physical memory 크기까지다.

```text
CPU virtual address 표현 범위
  -> 가능한 주소 이름의 상한

Pintos resident memory 한계
  -> 지금 실제 frame을 줄 수 있는 물리 자원과 VM 정책의 한계
```

그래서 큰 user virtual address space가 있어도 모든 page가 동시에 RAM에 올라와야 하는 것은 아니다. 필요한 page만 resident가 되고, 나머지는 unmapped, lazy, file-backed, swap-backed 상태로 metadata에 남을 수 있다.

## 14. 자주 생기는 오해 정리

### kernel direct map은 user memory 복사본인가?

아니다. kernel direct map은 physical RAM frame의 alias다. 복사본이 아니다.

### active PML4 전환은 user pool 전환인가?

아니다. active PML4 전환은 user VA 해석 규칙의 전환이다. user pool은 전역 physical frame 자원으로 남는다.

### page table만 있으면 SPT는 필요 없나?

Project 3 VM에서는 부족하다. page fault 처리와 resource management를 위해 page의 type, backing store, lazy state 같은 추가 metadata가 필요하다.

### direct map은 page identity인가?

아니다. direct map은 현재 RAM frame의 내용을 보여 준다. page가 evict되면 page identity는 metadata/backing store에 남고, frame은 다른 용도로 바뀔 수 있다.

## 15. 마지막으로 다시 압축하기

이 글을 한 번에 기억하려면 네 문장으로 충분하다.

**kernel VA는 전역 view다.**  
process가 바뀌어도 kernel mapping은 같은 위치에 유지된다.

**direct map은 physical RAM의 kernel-side alias다.**  
user pool frame도 RAM에 올라와 있으면 kernel direct-map VA로 접근할 수 있다.

**user VA는 active PML4에 따라 달라지는 process별 view다.**  
같은 `0x500000`도 Process A와 Process B에서 다른 frame을 볼 수 있다.

**VM metadata는 page의 정체성과 복구 방법을 기억한다.**  
page fault가 나면 OS가 metadata를 보고 frame을 확보하고, direct-map VA로 내용을 채운 뒤, user page table mapping을 다시 만든다.

결국 VM의 구조는 주소를 크게 보이게 하는 기술이라기보다, **주소 이름, frame byte, mapping, metadata, backing store를 분리해서 관리하는 구조**에 가깝다. kernel과 user memory의 차이는 이 구조 안에서 “어느 view가 전역이고, 어느 view가 process별인가”로 정리된다.
