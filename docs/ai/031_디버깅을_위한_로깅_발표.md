# 디버깅을 위한 로깅

> AI에게 바로 물어보기 전에, 내가 직접 확인 가능한 증거를 남기는 방법

이 문서는 슬라이드보다는 발표 형태의 포스팅 초안이다. 최종 결과물은 `DESIGN.md`를 참고해 single HTML로 만들 예정이며, HTML에서 넣을 시각 효과는 `TODO(HTML)`로 남겨 둔다.

## 0. 발표 의도

내가 이 자료를 만들려는 이유는 단순하다.

버그가 났을 때 AI에게 바로 물어보면 빠를 때가 있다. 그런데 계속 그렇게 하면 내가 직접 원인을 좁히는 힘이 약해진다. 특히 Pintos처럼 실행 흐름이 복잡하고, kernel panic이나 page fault가 섞이는 과제에서는 AI가 그럴듯한 원인을 말해도 실제로 맞는지 검증해야 한다.

그래서 이 발표의 목표는 "AI를 쓰지 말자"가 아니다. 더 정확히는 다음 순서를 습관으로 만들자는 것이다.

1. 먼저 로그로 실제 실행 흐름을 본다.
2. 로그에서 이상한 지점을 찾는다.
3. 그 다음에 문서, 코드, AI, 팀원에게 물어본다.

로그는 버그의 정답을 자동으로 알려 주지 않는다. 대신 추측을 관찰 가능한 증거로 바꿔 준다.

## 1. 로깅이란?

로깅은 프로그램이 실행되는 동안 "지금 어디를 지나고 있고, 어떤 값을 보고 있는지"를 기록하는 일이다.

`printf("here\n")`도 로그다. 하지만 디버깅에 쓰기 좋은 로그는 조금 더 구조가 있다.

```text
[DBG] fn=load_user k=call args={name="echo"}
[DBG] fn=load_user k=branch expr="file == NULL" value=0
[DBG] fn=load_user k=return value=true
```

이런 로그는 나중에 검색하기 쉽다.

- `fn=load_user`로 특정 함수만 볼 수 있다.
- `k=branch`로 조건문 판단만 볼 수 있다.
- `k=return`으로 어디서 빠져나갔는지 볼 수 있다.
- `args={...}`, `vals={...}`로 당시 상태를 확인할 수 있다.

Pintos 공식 reference도 `printf()`의 가치를 낮게 보지 말라고 설명한다. Pintos의 `printf()`는 kernel thread나 interrupt handler 같은 곳에서도 꽤 넓게 사용할 수 있고, 서로 다른 문자열을 여러 지점에 넣어 문제가 발생한 구간을 좁히는 전략을 소개한다.

다만 이 자료에서는 "아무 데나 많이 찍자"보다 한 단계 더 나아가, 나중에 분석하기 쉬운 형식으로 찍는 방법을 다룬다.

## 2. 왜 그냥 디버거나 AI를 쓰지 않나?

디버거는 좋다. AI도 도움이 된다. 하지만 로그가 필요한 순간이 있다.

디버거는 한 시점의 상태를 깊게 보는 데 좋다. 반면 로그는 여러 실행 지점을 한 번에 펼쳐서 보는 데 좋다. 특히 "어느 함수까지 갔는지", "반복 중 어느 순간 값이 깨졌는지", "여러 thread 중 누가 먼저 실행됐는지" 같은 질문은 로그가 편할 때가 많다.

AI는 원인 후보를 빠르게 말해 줄 수 있다. 하지만 AI가 보는 것은 보통 내가 제공한 정보뿐이다. 내가 로그 없이 "fork가 이상하게 터져요"라고 말하면 AI도 넓은 범위의 추측을 할 수밖에 없다. 반대로 "두 번째 child의 cleanup 진입 직후 #GP가 나고, `rax=cccc...`와 `vm_try_handl value=0`이 보인다"라고 말하면 질문의 수준이 달라진다.

즉, 로그는 AI를 대체하는 도구라기보다, AI에게 물어보기 전에 질문을 더 정확하게 만드는 도구다.

## 3. 디버깅 로그는 어디에 찍나?

> 개인적으로 사용하는 법을 공유하는 것이다. 이 방식을 꼭 따를 필요는 없다.
> 
> 개인적으로는 The Grug Brained Developer의 Logging 섹션을 좋아한다. 한 번 읽어보는 것을 추천한다.

개인적으로 가장 자주 쓰는 위치는 다섯 곳이다.

### 3-1. 함수에 들어온 직후

함수의 입력값을 확인한다.

```text
[DBG] fn=open_file k=call args={path="a.txt" flags=0}
```

이 로그가 있으면 "이 함수가 호출됐는가?", "호출됐다면 어떤 인자로 들어왔는가?"를 바로 확인할 수 있다.

### 3-2. return 직전

반환값과 중요한 상태를 남긴다.

```text
[DBG] fn=open_file k=return value=-1 reason="not_found"
```

early return이 많은 함수에서는 특히 중요하다. 실패가 났을 때 "어느 return으로 빠졌는지"를 찾을 수 있기 때문이다.

### 3-3. 조건문 직전

조건문 안쪽에서 바로 로그를 찍기보다, 조건값 자체를 먼저 이름 붙여 찍는다.

```text
[DBG] fn=open_file k=branch expr="file == NULL" value=1
```

이렇게 하면 "왜 이 분기로 갔는지"가 남는다.

조건식이 복잡하다면 중간값을 변수처럼 이름 붙여 남기는 편이 좋다.

```text
[DBG] fn=check_access k=note vals={exists=1 owner=0 writable=1}
[DBG] fn=check_access k=branch expr="exists && (owner || writable)" value=1
```

실제 서비스에서는 request id, log level, 특정 사용자만 로그를 켜는 기능까지 중요하지만, Pintos에서는 단순한 `printf()` 기반 로그부터 시작하면 충분하다.

### 3-4. 반복문 시작, 반복 중, 반복 종료

반복문은 값이 조금씩 바뀌다가 어느 순간 깨지는 경우가 많다.

```text
[DBG] fn=copy_items k=loop.s expr="i < count" value=1 i=0 count=3
[DBG] fn=copy_items k=loop   expr="i < count" value=1 i=0 src=0x1000 dst=0x2000
[DBG] fn=copy_items k=loop   expr="i < count" value=1 i=1 src=0x1010 dst=0x2010
[DBG] fn=copy_items k=loop.e expr="i < count" value=0 i=3 count=3
```

반복문 로그는 너무 많아지기 쉽다. 그래서 전체 반복을 다 찍기보다, 의심되는 구간에서만 잠깐 켜는 식으로 사용한다.

### 3-5. 계산 중간값

어떤 값이 계산되어 다음 함수로 넘어간다면, 그 직전에 찍는다.

```text
[DBG] fn=load_segment k=calc vals={read_bytes=400 zero_bytes=3696 page=0x3ff000}
```

이런 로그는 "입력은 정상인데 계산 결과가 이상한지", "계산은 정상인데 다음 함수에서 깨지는지"를 나누는 데 도움이 된다.

## 4. 로그를 어떻게 분석하나?

로그 분석의 기본은 세 가지 질문이다.

1. 마지막으로 정상인 줄은 어디인가?
2. 처음으로 이상해진 줄은 어디인가?
3. 그 사이에서 어떤 값이 바뀌었는가?

예를 들어 숫자 문자열을 정수로 바꾸는 작은 함수가 있다고 하자. Pintos와 무관한 예시다.

```c
int
parse (const char *input) {
  printf ("[DBG] fn=parse k=call args={input=\"%s\"}\n", input);

  int acc = 0;

  for (int i = 0; input[i] != '\0'; i++) {
    char ch = input[i];

    printf ("[DBG] fn=parse k=loop   "
            "expr=\"input[i] != '\\0'\" value=1 i=%d ch='%c' acc=%d\n",
            i, ch, acc);

    bool is_digit = '0' <= ch && ch <= '9';

    if (!is_digit) {
      printf ("[DBG] fn=parse k=branch "
              "expr=\"is_digit(ch)\" value=0\n");
      printf ("[DBG] fn=parse k=return value=-1\n");
      return -1;
    }

    acc = acc * 10 + (ch - '0');
  }

  printf ("[DBG] fn=parse k=return value=%d\n", acc);
  return acc;
}
```

이 함수에 `parse("12x")`를 넣으면 이런 로그가 나온다.

```text
[DBG] fn=parse k=call args={input="12x"}
[DBG] fn=parse k=loop   expr="input[i] != '\0'" value=1 i=0 ch='1' acc=0
[DBG] fn=parse k=loop   expr="input[i] != '\0'" value=1 i=1 ch='2' acc=1
[DBG] fn=parse k=loop   expr="input[i] != '\0'" value=1 i=2 ch='x' acc=12
[DBG] fn=parse k=branch expr="is_digit(ch)" value=0
[DBG] fn=parse k=return value=-1
```

코드와 로그를 같이 보면 흐름이 이렇게 따라간다.

1. `k=call` 로그가 있으므로 `parse()`는 실제로 호출됐다.
2. 첫 번째 loop 로그에서 `i=0`, `ch='1'`, `acc=0`이다. 아직 누적 전 상태다.
3. 두 번째 loop 로그에서 `i=1`, `ch='2'`, `acc=1`이다. 첫 번째 문자는 정상 처리됐다.
4. 세 번째 loop 로그에서 `i=2`, `ch='x'`, `acc=12`다. 여기까지 보면 `1`, `2` 처리는 정상이다.
5. 바로 다음 `k=branch` 로그에서 `is_digit(ch)`가 false다. 즉 실패 원인은 세 번째 문자 `x`다.
6. `k=return value=-1`이 이어지므로 실패 반환은 그 조건문 안에서 발생했다.

여기서 중요한 점은 "parse가 실패했다"가 아니라 "어떤 입력의 어느 위치에서 어떤 조건이 false가 되어 실패했는지"까지 좁혔다는 것이다.

이 정도까지 좁힌 뒤에야 코드나 문서를 보면 훨씬 적은 범위를 읽게 된다.

## 5. Pintos에서 왜 더 유용한가?

Pintos에서는 버그가 단순한 함수 실패로 끝나지 않는 경우가 많다.

- kernel panic이 난다.
- page fault가 난다.
- interrupt context와 thread context가 섞인다.
- 같은 함수가 여러 thread에서 호출된다.
- 테스트 output과 kernel output이 섞여 보인다.

그래서 로그에 최소한의 실행 맥락을 같이 남기는 편이 좋다.

내가 사용하던 출력 패턴은 대략 이런 모양이었다.

```text
[DEG] r=thrd tid= 3 p4=0x8004247000 fn=load_segment k=call   args={file=0x8004240038 ofs=0 upage=0x3ff000}
[DEG] r=thrd tid= 3 p4=0x8004247000 fn=load_segment k=loop   expr="read_bytes > 0 || zero_bytes > 0" value=1 upage=0x3ff000
[DEG] r=thrd tid= 3 p4=0x8004247000 fn=load_segment k=return value=false
```

필드의 의미는 다음과 같다.

| 필드 | 의미 |
|---|---|
| `[DEG]` | grep하기 위한 고정 prefix |
| `r` | 실행 문맥. 예: thread, interrupt |
| `tid` | 현재 thread id |
| `p4` | 현재 thread의 page table 식별용 값 |
| `fn` | 로그를 찍은 함수 |
| `k` | event 종류. call, return, branch, loop, calc 등 |
| `args` | 함수 입력값 |
| `vals` | 중간 계산값 또는 관찰값 |

핵심은 로그를 예쁘게 만드는 것이 아니다. 나중에 `fn=...`, `k=return`, `tid=...` 같은 문자열로 바로 검색할 수 있게 만드는 것이다.

이 패턴은 외부 GitHub 참고 프로젝트에서 GitHub 계정 `YangSiJun528`, commit author name `sijun-yang`이 남긴 `debug_trace.h`와 그 사용 방식에서 가져온 것이다. 여기서는 Pintos 구현 로직을 소개하지 않고, 출력 형식과 사용 의도만 소개한다.

## 6. 실제 사례: 2026-05-12 `fork-multiple`

이 사례는 Pintos VM 작업 중 `fork-once`는 통과하지만 `fork-multiple`에서 실패하던 상황을 로그로 좁힌 기록이다.

주의: 이 섹션에는 VM의 fork/copy/kill 흐름과 자원 소유권에 관한 설명이 나온다. 아직 해당 파트를 직접 구현해보고 싶은 사람에게는 스포일러가 될 수 있다.

전체 로그는 아래 파일을 기준으로 본다.

- `docs/daily/files/001/fork-once.output`
- `docs/daily/files/001/fork-multiple.output`

아래 본문에 들어가는 로그는 발표 흐름을 설명하기 위한 발췌다. HTML로 만들 때 접어서 열 수 있는 로그 패널에는 이 두 파일의 전체 내용을 넣는다.

처음에는 이상한 주소 접근이 보였다.

```text
0x0047480000 - 스택 시작 위치
0x0100000000 - 이건 머임 대체?? 커널 영역도 아니고 스택 영역도 아닌, 접근하면 안되는 위치인데
0x80042490f0 - spt 위치
```

이 단계에서는 아직 원인을 모른다. "물리 주소를 가상 주소로 보고 있나?", "어디선가 잘못된 값이 들어가나?", "fork 과정에서 꼬였나?" 정도의 추측만 있었다.

### 6-1. 먼저 성공 기준을 본다

`fork-once`는 child 하나를 만들고, child가 종료된 뒤 child SPT cleanup까지 끝난다.

```text
Executing 'fork-once':
...
[DEG] r=thrd tid= 4 ... k=call   fn=supplemental args={copy dst=0x80042510f0 src=0x80042490f0}
...
[DEG] r=thrd tid= 4 ... k=return fn=supplemental value=true
(fork-once) child run
child: exit(81)
[DEG] r=thrd tid= 4 ... k=call   fn=supplemental args={kill spt=0x80042510f0}
[DEG] r=thrd tid= 4 ... k=return fn=supplemental void
(fork-once) Parent: child exit status is 81
(fork-once) end
fork-once: exit(0)
```

이 로그만 보면 `copy -> child 실행 -> child 종료 -> kill -> parent wait` 흐름은 한 번짜리 fork에서 정상이다.

### 6-2. 실패 로그를 같은 흐름으로 비교한다

`fork-multiple`에서도 첫 번째 child는 같은 흐름으로 종료된다.

```text
Executing 'fork-multiple':
...
[DEG] r=thrd tid= 4 ... k=call   fn=supplemental args={copy dst=0x80042510f0 src=0x80042490f0}
...
[DEG] r=thrd tid= 4 ... k=return fn=supplemental value=true
(fork-multiple) child run
child: exit(4)
[DEG] r=thrd tid= 4 ... k=call   fn=supplemental args={kill spt=0x80042510f0}
[DEG] r=thrd tid= 4 ... k=return fn=supplemental void
(fork-multiple) Parent: child exit status is 4
```

그 다음 두 번째 child도 copy 자체는 끝난다. 깨지는 지점은 child 실행 중이 아니라, child가 종료된 뒤 cleanup으로 들어간 직후다.

```text
[DEG] r=thrd tid= 5 ... k=call   fn=supplemental args={copy dst=0x80042520f0 src=0x80042490f0}
...
[DEG] r=thrd tid= 5 ... k=return fn=supplemental value=true
(fork-multiple) child run
child: exit(5)
[DEG] r=thrd tid= 5 ... k=call   fn=supplemental args={kill spt=0x80042520f0}
Interrupt 0x0d (#GP General Protection Exception) at rip=8004219b27
...
rax cccccccccccccccc ... rdx 000000800424b018
...
Kernel PANIC at ../../userprog/exception.c:89 in kill(): Kernel bug - unexpected interrupt in kernel
```

여기서 바로 볼 수 있는 사실은 다음과 같다.

- `fork-once`는 성공한다.
- `fork-multiple`의 첫 번째 child도 성공한다.
- 두 번째 child는 copy와 child 실행까지는 끝난다.
- panic은 두 번째 child의 `supplemental ... kill` 진입 직후에 난다.
- `rax=cccccccccccccccc`처럼 이미 망가졌거나 해제된 값처럼 보이는 단서가 있다.
- 따라서 처음부터 "fork 자체가 안 된다"가 아니라, 반복 fork에서 cleanup/소유권 문제가 터진다고 좁힌다.

### 6-3. page fault 로그로 한 번 더 좁힌다

panic 출력과 DEG 로그가 섞여 나오지만, 그 안에서도 다음 흐름은 읽을 수 있다.

```text
[DEG] r=thrd tid= 5 ... k=call   fn=vm_try_handl args={f=0x80042529b0 addr=0x421a04a user=0 write=0 not_present=1}
[DEG] r=thrd tid= 5 ... k=call   fn=spt_find_pag args={spt=0x80042520f0 va=0x421a000}
[DEG] r=thrd tid= 5 ... k=branch fn=spt_find_pag expr="is_not_found" value=1
...
[DEG] r=thrd tid= 5 ... k=branch fn=vm_try_handl expr="is_not_found" value=1
[DEG] r=thrd tid= 5 ... k=return fn=vm_try_handl value=0
Interrupt 0x0e (#PF Page-Fault Exception) at rip=8004216335
...
[DEG] r=thrd tid= 6 ... k=call   fn=supplemental args={init spt=0x80042580f0}
...
Kernel PANIC recursion at ../../userprog/exception.c:89 in kill().
```

이 구간에서 얻는 질문은 더 구체적이다.

- `tid=5`가 cleanup 중 접근한 `addr=0x421a04a`는 왜 사용자 페이지가 아니라 커널 쪽 흐름에서 fault를 만들었나?
- `spt_find_pag`가 `va=0x421a000`을 못 찾는 것은 정상인가?
- `vm_try_handl value=0`이 나온 뒤 왜 panic이 재귀적으로 이어졌나?
- `tid=6` 로그가 panic 출력 중간에 섞이는 것은 동시 실행/출력 interleaving으로 봐야 하나?

여기서 중요한 것은 로그 한 줄만 보고 단정하지 않는 것이다. `spt_find_pag`가 실패했다고 해서 그 함수가 원인이라고 바로 결론 내리지 않는다. 실패 지점 주변의 소유권, cleanup 순서, 이미 해제된 포인터 가능성을 같이 본다.

기록에는 이렇게 정리되어 있다.

```text
패닉 나기 전 코드가 supplemental_page_table_copy, supplemental_page_table_kill

여기서 보는 공유 자원이 문제일 것. 부모와 자식이 같이 보는 spt 등

이거 공유 자원 변수로 빼고 이름 붙이다보니까 명확해짐.
aux 를 부모거만 보고, 이게 uninit destroy에서 free 해줘서
2번째 자식이 free 하려고 하거나 aux 접근할 때 에러나는거임.
```

구현 관점의 결론은 `copy`와 `kill` 사이에서 공유되면 안 되는 자원, 특히 `aux`의 소유권과 해제 시점을 의심해야 한다는 것이었다. 이 내용은 구현 세부사항을 포함하므로 발표에서는 스포일러 패널로 분리한다.

이 사례에서 로그가 해 준 일은 정답을 출력하는 것이 아니었다. 대신 다음 질문으로 이끌었다.

- 실패가 매번 같은 child와 같은 cleanup 근처에서 나는가?
- 첫 번째 child와 두 번째 child의 차이는 무엇인가?
- copy와 kill 중 누가 공유 자원을 건드리는가?
- `aux`는 parent와 child가 따로 소유하는가, 공유하는가?
- free 이후 다시 접근하는 흐름이 있는가?

이 질문들이 생기면, 그때부터는 코드 읽기가 훨씬 쉬워진다. 전체 VM을 다시 보는 것이 아니라, copy/kill, aux 소유권, destroy 흐름만 보면 되기 때문이다.

다만 로그를 찍는다고 바로 답이 나온 것은 아니다. 문제 원인 파악, 로깅 추가, 디버깅, 수정, 결과 확인을 반복했고, 이 과정에 약 4시간이 걸렸다. 로그의 가치는 "정답을 알려준다"가 아니라 "다음에 볼 곳을 좁혀 준다"에 있다.

## 7. 출력 패턴을 만들 때의 원칙

내가 선호하는 원칙은 네 가지다.

### 7-1. grep 가능한 prefix를 붙인다

```text
[DEG]
```

이런 prefix 하나만 있어도 테스트 로그에서 내가 찍은 줄만 뽑아 보기 쉬워진다.

```text
grep "\\[DEG\\]" test.output
```

Pintos output에는 부팅 메시지, 테스트 메시지, panic 메시지가 섞인다. prefix가 없으면 내가 찍은 로그를 찾는 데 시간이 많이 든다.

### 7-2. 로그 종류를 짧게 고정한다

```text
k=call
k=return
k=branch
k=loop
k=calc
```

로그 종류가 고정되어 있으면, 실패할 때 보는 순서도 단순해진다.

1. `k=call`로 함수가 호출됐는지 본다.
2. `k=branch`로 조건 판단을 본다.
3. `k=loop`로 반복 중 값 변화를 본다.
4. `k=return`으로 빠져나간 위치를 본다.

### 7-3. 자주 필요한 맥락은 매번 자동으로 붙인다

Pintos에서는 `tid`, 실행 문맥, 현재 address space 관련 값이 자주 필요하다. 매번 직접 적으면 빠뜨리기 쉽다.

그래서 공통 로그 형식에 이런 값을 자동으로 붙이는 편이 좋다.

```text
r=thrd tid= 3 p4=0x8004247000
```

이 값이 있으면 "같은 함수 로그인데 서로 다른 thread의 로그가 섞인 상황"을 분리해서 볼 수 있다.

### 7-4. 켜고 끌 수 있어야 한다

Pintos 테스트는 예상 output과 실제 output을 비교한다. 디버깅 로그가 남아 있으면 테스트 결과를 깨뜨릴 수 있다.

그래서 로그를 추가할 때는 다음 중 하나가 필요하다.

- 제출 전에 반드시 제거한다.
- compile-time flag로 끈다.
- 특정 구간에만 임시로 넣고, 확인 후 되돌린다.

외부 참고 커밋에서도 interrupt에서 임시로 로그를 찍은 뒤, 잘 되는 것을 확인하고 되돌린 기록이 있다. 이 흐름 자체가 중요하다. 로그는 디버깅을 위한 임시 관찰 장치이지, 과제 제출물의 기능이 아니다.

## 8. 로그를 남길 때 조심할 점

### 8-1. 로그가 버그를 가릴 수 있다

로그 출력은 공짜가 아니다. 특히 interrupt, scheduling, timing이 얽힌 코드에서는 로그를 찍는 행위 자체가 실행 순서를 바꿀 수 있다.

그래서 로그를 보고 버그가 사라졌다면, "고쳤다"가 아니라 "관찰 때문에 타이밍이 바뀌었을 수 있다"라고 생각해야 한다.

### 8-2. 너무 많이 찍으면 분석이 어려워진다

처음부터 모든 함수에 다 찍으면 로그가 너무 커진다. 추천하는 방식은 다음과 같다.

1. 넓은 범위에 적은 로그를 찍는다.
2. 이상한 구간을 찾는다.
3. 그 구간 안에 더 자세한 로그를 추가한다.
4. 원인이 좁혀지면 불필요한 로그를 지운다.

Pintos reference가 설명하는 `<1>`, `<2>` 방식도 같은 원리다. 큰 구간을 먼저 나누고, 점점 작은 구간으로 들어간다.

### 8-3. 로그 형식이 매번 다르면 검색이 어렵다

```text
here
hello
AAAA
why?
```

이런 로그도 급할 때는 도움이 된다. 하지만 시간이 지나면 어떤 함수에서 찍은 것인지, 어떤 값이었는지 다시 봐야 한다.

가능하면 최소한 `fn`, `k`, `value` 정도는 남긴다.

```text
[DBG] fn=wait_child k=return value=-1
```

### 8-4. 로그는 검증을 대신하지 않는다

로그는 관찰이다. 최종 판단은 코드, 문서, 테스트 결과와 함께 해야 한다.

특히 Pintos에서는 reference 요구사항과 테스트가 중요하다. 로그로 어떤 흐름을 봤더라도, 그것이 과제 요구사항에 맞는지는 별도로 확인해야 한다.

## 9. FAQ

### Q1. 왜 AI에게 바로 물어보면 안 되나요?

안 되는 것은 아니다. 다만 로그 없이 물어보면 질문이 너무 넓다.

나쁜 질문:

```text
fork-multiple이 터지는데 왜 그런가요?
```

좋은 질문:

```text
fork-multiple에서 첫 번째 child는 끝나고,
두 번째 child도 copy와 child 실행까지는 끝납니다.
그런데 tid=5의 supplemental kill 진입 직후 #GP가 나고,
rax=cccccccccccccccc 및 vm_try_handle_fault value=0이 보입니다.
copy/kill 과정에서 aux 소유권이나 cleanup 순서 문제가 의심되는데,
어떤 불변식을 확인해야 할까요?
```

두 질문은 답변의 수준이 달라진다. 좋은 질문은 이미 로그 분석이 어느 정도 끝난 상태에서 나온다.

### Q2. 그러면 로그만 쓰면 되나요?

아니다. 로그, ASSERT, backtrace, GDB는 서로 역할이 다르다.

- 로그: 실행 흐름과 값 변화를 시간순으로 본다.
- ASSERT: 깨지면 안 되는 조건을 즉시 검증한다.
- backtrace: panic 시점의 호출 경로를 본다.
- GDB: 특정 시점의 상태를 깊게 본다.

이 발표는 그중에서도 "가장 쉽게 시작할 수 있는 printf 로그"에 초점을 둔다.

### Q3. 실제 서비스에서는 이렇게 안 하나요?

실제 서비스에서는 보통 더 체계적인 로깅 라이브러리를 쓴다.

- log level
- request id
- user id
- structured logging
- log aggregation
- sampling

하지만 이 발표의 대상은 Pintos를 하면서 디버깅 습관을 만드는 사람이다. 지금은 단순한 `printf()` 로그만으로도 충분히 많은 것을 배울 수 있다.

### Q4. 로그를 제출 코드에 남겨도 되나요?

Pintos에서는 조심해야 한다. 테스트는 예상 output을 기준으로 채점되므로, 불필요한 debug output이 남으면 통과하던 테스트도 실패할 수 있다.

따라서 디버깅 로그는 제출 전에 제거하거나 꺼야 한다.

### Q5. 로그를 잘 찍는 기준은 뭔가요?

좋은 로그는 많이 찍은 로그가 아니라, 다음 질문에 답할 수 있는 로그다.

- 어떤 함수에 들어왔는가?
- 어떤 인자로 들어왔는가?
- 어떤 조건이 true/false였는가?
- 반복 중 어떤 값이 바뀌었는가?
- 어디서 어떤 값으로 반환했는가?
- 여러 thread 중 누가 찍은 로그인가?

이 질문에 답할 수 있으면 충분하다.

## 10. 마무리

디버깅은 추측 게임이 아니다.

처음에는 원인을 모를 수 있다. 당연하다. 하지만 모르는 상태에서 바로 정답을 찾으려고 하면, AI에게 의존하거나, 전체 코드를 무작정 읽거나, 의미 없는 삽질을 하게 된다.

로그를 남기면 질문이 바뀐다.

```text
왜 터지지?
```

에서

```text
여기까지는 정상이고, 이 조건부터 이상하다.
```

로 바뀐다.

이 차이가 크다. 로그는 나 대신 생각해 주지 않는다. 하지만 내가 생각할 수 있는 재료를 남겨 준다.

그래서 Pintos에서 버그를 만나면, 먼저 간단한 `printf()` 로그부터 남겨 보자. 함수 호출, 분기, 반복, 반환을 찍고, 마지막 정상 지점과 처음 이상한 지점을 찾자. 그 다음에 문서든, 팀원이든, AI든 물어보면 된다.
