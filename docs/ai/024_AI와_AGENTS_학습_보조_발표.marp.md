# 1. 먼저 기준 정하기

```text
AI 활용: 요구사항 분석, 막혔을 때 확인할 방향 잡기
직접 수행: 코드 작성, 리팩토링, 최종 판단
```

`docs/ai/003_pintos_ASSERT_발표.marp.md`

<!--

코드 작성과 최종 판단은 직접 하는 쪽으로 두었습니다.
-->

# 2. 기존 문제

- 외부 Pintos 자료는 과제 버전과 다를 수 있음
- KAIST 자료도 CS330/EE415, 64-bit/32-bit가 섞임
- 코치님들도 외부 해답 의존은 추천하지 않음
- AI는 물어보면 구현 코드를 너무 쉽게 보여줌

```text
외부 자료는 불확실하거나 과제 조건과 다를 수 있다.
kaist-oslab-pintos-slides-* 계열은 EE415/32-bit 설명이 섞여 있다.
```

<!--
기존 문제는 신뢰도와 통제였습니다.
외부 자료는 버전이 다를 수 있고, AI는 막히면 구현 코드를 바로 보여주기 쉬웠습니다.
그래서 그냥 AI에게 묻는 방식으로는 학습 보조가 아니라 정답 검색이 될 수 있었습니다.
-->

# 4. `AGENTS.md` 작성

```text
Pintos 구현과 직접 관련된 답변은 docs/reference 아래의 reference 파일을 기준으로 한다.

Pintos 과제 구현 코드를 통째로 생성하거나 패치로 작성하지 않는다.

외부 Pintos 해답, GitHub 구현, 블로그 구현 코드를 찾아 읽거나 요약하지 않는다.
```

<!--
이 규칙을 매번 말하지 않으려고 `AGENTS.md`에 고정했습니다.
reference 우선순위, 외부 해답 금지, 구현 코드 생성 금지를 적어 AI 행동을 제한했습니다.
-->

# 5. 결과: 코드보다 근거

```text
요청: 함수 만들어서 is valid 이런 식으로 써서 먼저 종료하기
응답: 좋습니다. 직접 패치는 안 하고, 현재 구조 기준으로
      어디 앞단에서 막아야 하는지만 정확히 짚겠습니다.
```

```text
요청: 지금 git 변경사항 보고 테스트 ㄱㄱ
응답: 테스트는 repo 지침상 제가 직접 실행하지 않았고,
      대신 diff 검토와 git diff --check만 했습니다.
```

<!--
효과는 실제로 있었습니다.
구현으로 흘러갈 수 있는 요청에도 코드 대신 요구사항과 범위를 정리했습니다.
테스트도 직접 돌리지 않고, 확인할 명령이나 결과 위치를 안내하는 쪽으로 바뀌었습니다.
-->
