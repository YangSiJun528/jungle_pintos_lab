## 1. Thread와 Context Switch

가장 먼저 thread가 어떤 상태를 가지는지부터 잡는 것이 좋다. `Threads appendix`는 `THREAD_RUNNING`, `THREAD_READY`, `THREAD_BLOCKED`, `THREAD_DYING`을 설명한다. 같은 문서는 `struct thread`가 thread 또는 user process를 나타내며, 한 페이지 안에서 kernel stack과 함께 배치된다고 설명한다.

`Context Switch` 전사본은 `struct thread`가 thread id, status, priority, kernel stack 관련 정보, page table pointer 등을 포함한다고 설명한다. 또한 Pintos에는 ready list와 all list가 있으며, ready list는 실행 준비가 된 thread들의 집합이고 all list는 시스템의 모든 thread 집합이라고 설명한다.

이 단계에서 볼 핵심 함수 이름은 자료에 언급된 범위 안에서 `thread_create()`, `thread_block()`, `thread_yield()`, `thread_exit()`, `schedule()`, `switch_threads()`, `thread_schedule_tail()`이다. `schedule()`은 exit, block, yield 상황에서 호출된다고 설명되며, context switch는 현재 thread의 context를 stack에 저장하고 다음 thread의 context를 복원하는 과정으로 설명된다.

## 2. Synchronization

Project1 introduction은 synchronization이 중요하다고 말하면서, 모든 synchronization 문제를 interrupt disable로 해결하지 말라고 경고한다. 대신 semaphore, lock, condition variable을 주로 사용하라고 설명한다.

`Synchronization appendix`에서 먼저 확인할 내용은 다음이다.

- interrupt disable은 kernel thread와 external interrupt handler 사이의 공유 데이터를 다룰 때 주로 필요하다.
- interrupt handler는 sleep할 수 없으므로 일반적인 lock을 사용할 수 없다.
- semaphore는 down/up 연산을 제공한다.
- lock은 초기값 1인 semaphore와 비슷하지만, lock을 얻은 thread만 release할 수 있다.
- condition variable은 monitor 안에서 조건을 기다리거나 signal/broadcast하는 데 사용된다.

Project1 introduction은 제출물에 busy waiting이 없어야 하며, `thread_yield()`를 tight loop에서 호출하는 것도 busy waiting의 한 형태라고 설명한다.

## 3. Alarm Clock

[Alarm Clock](../reference/pintos-kaist-original/project1/alarm_clock.md)은 `devices/timer.c`의 `timer_sleep()`을 다시 구현하라고 요구한다. 문서에 따르면 기존 구현은 현재 시간을 반복해서 확인하고 `thread_yield()`를 호출하는 busy waiting 방식이다.

여기서 이해해야 할 핵심은 다음이다.

- `timer_sleep()`은 호출한 thread의 실행을 최소 지정 tick만큼 멈춘다.
- tick 단위는 `TIMER_FREQ`와 관련되며 기본값은 100이다.
- `timer_msleep()`, `timer_usleep()`, `timer_nsleep()`은 필요할 때 `timer_sleep()`을 호출하므로 직접 수정할 필요가 없다고 설명된다.
- Project1 introduction은 alarm clock에서 timer interrupt가 sleeping thread를 깨워야 한다고 설명한다.

`Project1-1 Thread` 전사본은 현재 `timer_sleep()`이 ready state와 running state 사이를 오가며 CPU cycle을 사용한다고 설명한다. 전사본은 이를 sleep/wakeup 기반 alarm clock으로 바꾸는 흐름을 설명하며, blocked state, sleep queue, global tick, local tick, timer interrupt handler에서 깨울 thread를 찾는 내용을 언급한다.

따라서 Alarm Clock을 공부할 때는 `timer_sleep()`, busy waiting, blocked state, timer interrupt, tick 개념을 한 묶음으로 보면 된다.

## 4. Priority Scheduling

[Priority Scheduling](../reference/pintos-kaist-original/project1/priority_scheduling.md)은 priority scheduling과 priority donation을 구현하라고 요구한다. priority 범위는 `PRI_MIN (0)`부터 `PRI_MAX (63)`까지이며, 숫자가 클수록 높은 priority다. 기본 priority는 `PRI_DEFAULT (31)`로 설명된다.

문서와 전사본에서 공통으로 강조하는 핵심은 다음이다.

- ready list에 현재 실행 중인 thread보다 높은 priority의 thread가 추가되면 현재 thread가 즉시 processor를 양보해야 한다.
- lock, semaphore, condition variable에서 기다리는 thread 중 가장 높은 priority thread가 먼저 깨어나야 한다.
- thread는 자기 priority를 올리거나 내릴 수 있다.
- priority를 낮춘 결과 현재 thread가 더 이상 최고 priority가 아니면 CPU를 양보해야 한다.
- `thread_set_priority()`와 `thread_get_priority()`를 구현해야 한다.

`Project1-1 Thread` 전사본은 priority scheduling에서 ready list를 thread priority 기준으로 다루는 것, synchronization primitive의 wait list도 priority 기준으로 다루는 것, preemption point가 thread가 ready list에 들어갈 때라는 점을 설명한다.

## 5. Priority Donation

Priority Scheduling 문서는 priority inversion 예시를 통해 priority donation을 설명한다. 높은 priority thread가 낮은 priority thread가 들고 있는 lock을 기다리고, 중간 priority thread가 ready list에 있는 상황에서 문제가 발생한다고 설명한다.

문서에서 요구하는 priority donation의 범위는 다음이다.

- lock을 기다리는 높은 priority thread가 lock holder에게 priority를 donation한다.
- multiple donations를 처리해야 한다.
- nested donation을 처리해야 한다.
- 필요하면 nested donation 깊이에 합리적인 제한을 둘 수 있다.
- priority donation은 lock에 대해 구현하면 되고, 다른 synchronization construct에는 구현하지 않아도 된다.

`Project1-1 Thread` 전사본도 priority inversion, priority donation, nested donation, multiple donation을 설명한다. 전사본은 multiple donation을 위해 donors list를 유지하는 내용과 nested donation을 위해 기다리는 lock을 유지하는 내용을 언급한다. FAQ는 priority donation이 donor의 priority를 바꾸는 것이 아니라 donee thread의 priority에 영향을 준다고 설명하고, `thread_set_priority()`와 donation의 관계도 다룬다.

## 6. Advanced Scheduler

[Advanced Scheduler](../reference/pintos-kaist-original/project1/advanced_scheduler.md)는 4.4BSD scheduler와 비슷한 multilevel feedback queue scheduler를 구현하라고 요구한다. 문서는 priority scheduler가 동작하는 상태에서 advanced scheduler를 시작하는 것을 권장하며, advanced scheduler는 priority donation을 포함하지 않는다고 설명한다.

여기서 읽어야 할 핵심은 다음이다.

- `-mlfqs` option이 `thread_mlfqs`를 true로 설정한다.
- 4.4BSD scheduler가 enabled되면 thread는 자기 priority를 직접 제어하지 않는다.
- nice 값은 -20부터 20까지이며, 0이 기본값이다.
- priority는 `PRI_MAX - (recent_cpu / 4) - (nice * 2)`로 계산된다.
- `recent_cpu`는 최근 CPU 사용량의 추정값으로 설명된다.
- `load_avg`는 ready thread 수의 moving average로 설명된다.
- `recent_cpu`와 `load_avg`는 real number이므로 fixed-point arithmetic이 필요하다고 설명된다.

`Project1-2 BSD` 전사본도 nice, priority 계산, `recent_cpu`, decay, `load_avg`, fixed-point arithmetic을 차례로 설명한다. 전사본은 every fourth tick에서 priority를 다시 계산하고, every clock tick에서 running thread의 `recent_cpu`를 증가시키며, every second에서 `recent_cpu`와 `load_avg`를 갱신하는 규칙을 정리한다.

## 핵심 정리

1주차의 중심은 `Project1: Threads`다. 자료에서 반복해서 등장하는 축은 thread 상태와 context switch, synchronization, alarm clock의 busy waiting 제거, priority scheduling, priority donation, advanced scheduler다.

먼저 thread와 synchronization의 용어를 잡고, 그 다음 Alarm Clock을 통해 busy waiting과 timer tick을 이해한다. 이후 Priority Scheduling에서 priority 기준의 scheduling과 synchronization waiters를 보고, Priority Donation에서 priority inversion, nested donation, multiple donation을 확인한다. 마지막으로 Advanced Scheduler에서 4.4BSD scheduler, nice, `recent_cpu`, `load_avg`, fixed-point arithmetic을 읽는 순서가 자료 흐름과 가장 잘 맞는다.
