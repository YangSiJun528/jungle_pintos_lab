디버깅을 위한 로깅

버그가 났을 때 정답을 바로 찾으려 하기보다, 먼저 실행 흐름과 상태를 기록해서 추측을 관찰 가능한 증거로 바꾸는 방법을 정리한다.

2
Observe로그로 실제 실행 흐름을 본다.

0. 발표 의도

로그는 정답이 아니라 증거를 준다

버그가 났을 때 AI에게 바로 물어보면 빠를 때가 있다. 하지만 계속 그렇게 하면 직접 원인을 좁히는 힘이 약해진다. Pintos처럼 kernel panic, page fault, thread 실행 흐름이 섞이는 과제에서는 AI 답변도 결국 검증해야 한다.

먼저 본다

함수 호출, 조건, 반복, 반환을 로그로 남겨 실제 실행 흐름을 확인한다.

좁힌다

마지막 정상 지점과 처음 이상해진 지점 사이의 값 변화를 본다.

그 다음 묻는다

로그로 질문을 구체화한 뒤 문서, 코드, AI, 팀원에게 확인한다.

1. 로깅이란?

검색 가능한 실행 기록

로깅은 프로그램이 실행되는 동안 지금 어디를 지나고 있고, 어떤 값을 보고 있는지 기록하는 일이다. 단순한 printf("here\n")도 로그지만, 디버깅에 쓰기 좋은 로그는 나중에 검색하고 비교할 수 있는 구조가 있다.

구조가 있는 로그fn, k, args, value
[DBG] fn=load_user k=call args={name="echo"}[DBG] fn=load_user k=branch expr="file == NULL" value=0[DBG] fn=load_user k=return value=true

Pintos 공식 reference도 printf()를 과소평가하지 말라고 설명한다. 여러 지점에 서로 다른 문자열을 넣어 문제가 발생한 구간을 좁히는 전략을 직접 소개한다.

2. 왜 필요한가?

AI에게 묻기 전에 질문을 좁힌다

디버거는 한 시점의 상태를 깊게 보는 데 좋고, 로그는 여러 실행 지점을 시간순으로 펼쳐 보는 데 좋다. AI는 원인 후보를 말해줄 수 있지만, 로그 없이 질문하면 넓은 추측을 받을 가능성이 크다.

3. 어디에 찍나?

호출, 분기, 반복, 반환

개인적으로 사용하는 방법이다. 꼭 이 방식을 따를 필요는 없지만, 함수 호출 직후와 반환 직전, 조건문 직전, 반복문 시작과 중간, 계산 중간값은 자주 도움이 된다.

call

함수에 들어온 직후

이 함수가 실제로 호출됐는지, 호출됐다면 어떤 인자로 들어왔는지 확인한다.

exampleargs
[DBG] fn=open_file k=call args={path="a.txt" flags=0}
return

return 직전

early return이 많은 함수에서는 어느 경로로 빠졌는지 찾기 쉽다.

4. 로그 분석

코드와 로그를 같이 따라간다

로그 분석의 기본은 마지막으로 정상인 줄, 처음으로 이상해진 줄, 그 사이에서 바뀐 값을 찾는 것이다. Pintos와 무관한 작은 함수로 먼저 보자.

toy codeparse("12x")
int
parse (const char *input) {
  printf ("[DBG] fn=parse k=call args={input=\"%s\"}\n", input);

  int acc = 0;

  for (int i = 0; input[i] != '\0'; i++) {
    char ch = input[i];

    printf ("[DBG] fn=parse k=loop   "
            "expr=\"input[i] != '\\0'\" value=1 i=%d ch='%c' acc=%d\n",
            i, ch, acc);

    bool is_digit = '0' <= ch && ch <= '9';

    if (!is_digit) {
      printf ("[DBG] fn=parse k=branch "
              "expr=\"is_digit(ch)\" value=0\n");
      printf ("[DBG] fn=parse k=return value=-1\n");
      return -1;
    }

    acc = acc * 10 + (ch - '0');
  }

  printf ("[DBG] fn=parse k=return value=%d\n", acc);
  return acc;
}

5. Pintos 패턴

실행 맥락을 같이 남긴다

Pintos에서는 kernel panic, page fault, interrupt context, 여러 thread의 로그가 섞인다. 그래서 로그에 현재 문맥과 thread 식별자를 같이 남기는 편이 좋다.

DEG trace formatdebug_trace.h 사용 패턴
[DEG] r=thrd tid= 3 p4=0x8004247000 fn=load_segment k=call   args={file=0x8004240038 ofs=0 upage=0x3ff000}[DEG] r=thrd tid= 3 p4=0x8004247000 fn=load_segment k=loop   expr="read_bytes > 0 || zero_bytes > 0" value=1 upage=0x3ff000[DEG] r=thrd tid= 3 p4=0x8004247000 fn=load_segment k=return value=false
[DEG]grep하기 위한 고정 prefix
r실행 문맥. thread 또는 interrupt
tid현재 thread id
p4현재 thread의 page table 식별용 값
fn로그를 찍은 함수
kcall, return, branch, loop, calc 같은 event 종류
args / vals입력값과 중간 계산값

이 패턴은 외부 GitHub 참고 프로젝트에서 GitHub 계정 YangSiJun528, commit author name sijun-yang이 남긴 debug_trace.h와 사용 방식에서 가져온 것이다. 여기서는 Pintos 구현 로직이 아니라 출력 형식과 사용 의도만 다룬다.

6. 실제 사례

2026-05-12 fork-multiple

이 사례는 Pintos VM 작업 중 fork-once는 통과하지만 fork-multiple에서 실패하던 상황을 로그로 좁힌 기록이다. 실제 출력의 핵심 구간을 접어 두고, 먼저 직접 읽은 뒤 하이라이트를 켤 수 있게 했다.

스포일러 주의. 이 섹션에는 VM의 fork/copy/kill 흐름과 자원 소유권에 관한 원인 해설이 나온다. 아직 해당 파트를 직접 풀어보고 싶은 사람은 아래의 “디버깅 단서”와 “원인 해설” 패널을 열지 않는 편이 좋다.

로그에서 읽을 핵심 단서 열기

하이라이트를 켜기 전에는 아래 순서만 생각하면서 읽는다. “어느 child까지 정상인가?”, “정상 구간과 깨지는 구간의 함수 이름이 어디서 갈리는가?”, “패닉 직전 값이 말이 되는가?”

reading noteshighlight 토글 대상
1. fork-once는 child 하나를 만들고 copy - child exit - kill - parent wait 순서로 정상 종료한다.
2. fork-multiple에서도 첫 번째 child(tid=4)는 같은 순서로 정상 종료한다.
3. 두 번째 child(tid=5)는 copy가 끝난 뒤 child: exit(5)까지 출력된다.
4. 깨지는 위치는 child 실행 중이 아니라 tid=5의 supplemental kill 진입 직후다.
5. #GP에서 rax=cccccccccccccccc, rdx/rsi/rdi=0x800424b018이 같이 보인다.
6. 이어서 vm_try_handle_fault가 addr=0x421a04a를 처리하려고 하지만 spt_find_page가 va=0x421a000을 못 찾는다.
7. vm_try_handle_fault value=0 이후 #PF와 Kernel PANIC recursion이 이어진다.
8. 그래서 처음부터 “fork 자체가 실패했다”가 아니라, 반복 fork에서 cleanup/소유권 문제가 터졌다고 좁힌다.
원인 해설 열기
1. 비교 기준

fork-once와 fork-multiple의 첫 child는 같은 흐름으로 종료된다. 기준선은 깨지지 않았다.

2. 이상 신호

tid=5 kill 직후 #GP가 나고, rax=cccc...와 같은 비정상 값이 보인다.

3. 좁힌 위치

supplemental_page_table_copy와 supplemental_page_table_kill 사이의 aux/소유권과 cleanup 순서를 봤다.

이 사례에서 로그가 곧바로 정답을 출력해 준 것은 아니다. 로그를 추가하고, 실패 지점을 보고, 수정하고, 다시 결과를 확인하는 과정을 반복했다.

7. 출력 원칙

나중에 찾기 쉽게 만든다

로그는 예쁜 문장이 아니라 분석 도구다. 같은 prefix와 짧은 event kind를 쓰고, 자주 필요한 맥락은 자동으로 붙이는 편이 좋다.

grep 가능한 prefix

[DEG] 같은 고정 prefix가 있으면 부팅 메시지, 테스트 출력, panic 메시지 사이에서 내 로그만 뽑기 쉽다.

grepfilter
grep "\\[DEG\\]" test.output

짧은 로그 종류

k=call, k=return, k=branch, k=loop, k=calc처럼 고정한다.

반복되는 맥락

r=thrd tid=3 p4=... 같은 값은 매번 붙이면 thread가 섞인 로그를 분리해 볼 수 있다.

켜고 끄기

Pintos 테스트는 output을 비교하므로 debug output이 남으면 실패할 수 있다. 제출 전 제거하거나 compile-time flag로 끈다.

8. 주의점

로그도 실행에 영향을 준다

로그 출력은 공짜가 아니다. 특히 interrupt, scheduling, timing이 얽힌 코드에서는 출력 자체가 실행 순서를 바꿀 수 있다.

버그를 가릴 수 있다

로그를 넣었더니 버그가 사라졌다면 고친 것이 아니라 타이밍이 바뀐 것일 수 있다.

너무 많으면 어렵다

넓은 범위에 적은 로그를 찍고, 이상한 구간을 찾은 뒤 그 구간만 자세히 본다.

검증은 별도다

로그는 관찰이다. 최종 판단은 reference 요구사항, 코드, 테스트 결과와 함께 해야 한다.

9. FAQ

자주 나오는 질문

이 발표는 로깅만 쓰자는 이야기가 아니다. 가장 쉽게 시작할 수 있는 도구로서 printf 로그를 다루는 것이다.

왜 AI에게 바로 물어보면 안 되나요?

안 되는 것은 아니다. 다만 로그 없이 물어보면 질문이 너무 넓다. 로그로 “어디까지 정상이고 어디서 이상해졌는지”를 좁힌 뒤 묻는 것이 더 좋다.

그러면 로그만 쓰면 되나요?

아니다. 로그는 실행 흐름과 값 변화를 시간순으로 보는 도구다. ASSERT는 깨지면 안 되는 조건을 검증하고, backtrace는 panic 시점의 호출 경로를 보여주며, GDB는 특정 시점의 상태를 깊게 본다.

실제 서비스에서도 이렇게 하나요?

실제 서비스에서는 log level, request id, structured logging, aggregation 같은 더 체계적인 도구를 쓴다. Pintos 학습 단계에서는 단순한 printf() 로그만으로도 충분히 많은 것을 배울 수 있다.

로그를 제출 코드에 남겨도 되나요?

조심해야 한다. Pintos 테스트는 예상 output을 기준으로 채점되므로, 불필요한 debug output이 남으면 통과하던 테스트도 실패할 수 있다. 제출 전 제거하거나 꺼야 한다.

좋은 로그의 기준은 뭔가요?

어떤 함수에 들어왔는지, 어떤 인자인지, 어떤 조건이 true/false였는지, 반복 중 어떤 값이 바뀌었는지, 어디서 반환했는지, 여러 thread 중 누가 찍은 로그인지 답할 수 있으면 충분하다.

10. 마무리

디버깅은 추측 게임이 아니다

로그를 남기면 질문이 “왜 터지지?”에서 “여기까지는 정상이고, 이 조건부터 이상하다”로 바뀐다. 로그는 나 대신 생각해 주지 않지만, 내가 생각할 수 있는 재료를 남겨 준다.
