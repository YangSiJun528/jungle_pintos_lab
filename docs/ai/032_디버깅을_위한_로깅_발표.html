00. 발표 의도

AI를 쓰기 전에 증거를 남긴다

왜 이런 자료를 만들었는지부터 적어둔다. AI를 쓰지 말자는 얘기는 아니고, 물어보기 전에 내가 본 증거를 조금이라도 챙기자는 쪽에 가깝다.

버그가 났을 때 AI에게 바로 물어보면 빠를 때가 있다. 하지만 Pintos처럼 실행 흐름이 복잡하고 kernel panic, page fault, thread interleaving이 섞이는 과제에서는 AI의 설명도 실제 로그로 검증해야 한다.

이 발표의 목표는 AI를 쓰지 말자는 것이 아니다. 먼저 로그로 실행 흐름을 보고, 이상한 지점을 찾고, 그 다음에 문서와 코드와 AI를 보는 순서를 습관으로 만들자는 것이다.

로그는 버그의 정답을 자동으로 알려 주지 않는다. 대신 어디까지가 정상이고 어디서부터 이상한지 확인할 수 있는 재료를 남긴다.

01. 로깅이란?

실행 중 지나간 위치와 값을 기록하는 일

여기서는 그냥 printf도 로그라고 보고 시작한다. 다만 나중에 다시 보려면 최소한 검색할 수 있는 모양이면 좋다.

디버깅에 쓰기 좋은 로그는 검색할 수 있는 구조를 가진다. 함수 이름, 이벤트 종류, 인자, 반환값이 고정된 형태로 남으면 나중에 필요한 줄만 빠르게 좁힐 수 있다.

Pintos 문서에서도 printf()로 구간을 좁히는 얘기가 나온다. 여기서는 거기에 이름을 조금 붙여서, 나중에 grep하기 편하게 만드는 정도만 더한다.

검색 단위

fn=load_user로 특정 함수만 보고, k=branch로 조건 판단만 보고, k=return으로 빠져나간 위치만 볼 수 있다.

02. 디버거나 AI만 쓰지 않는 이유

로그가 있으면 덜 막연하다

디버거나 AI가 별로라는 얘기는 아니다. 다만 로그가 있으면 내가 뭘 물어봐야 하는지가 훨씬 선명해진다.

디버거는 한 시점의 상태를 깊게 보는 데 좋다. 반면 로그는 여러 실행 지점을 한 번에 펼쳐서 보는 데 좋다. 어느 함수까지 갔는지, 반복 중 어느 순간 값이 깨졌는지, 여러 thread 중 누가 먼저 실행됐는지 같은 질문은 로그가 편할 때가 많다.

AI도 원인 후보를 빠르게 말할 수 있다. 하지만 로그 없이 “fork가 이상하게 터진다”고 말하면 AI도 넓은 추측을 할 수밖에 없다. 반대로 “두 번째 child의 cleanup 진입 직후 #GP가 나고, rax=cccc...와 vm_try_handl value=0이 보인다”고 말하면 질문의 수준이 달라진다.

03. 어디에 찍나?

대충 찍을 위치 정해두기

아무 데나 막 찍으면 나중에 보기 힘들다. 내가 자주 찍는 위치만 몇 개 적어둔다.

개인적으로 자주 쓰는 위치는 함수 진입, return 직전, 조건문 직전, 반복문, 계산 중간값이다. 핵심은 많이 찍는 것이 아니라, 나중에 흐름을 복원할 수 있게 찍는 것이다.

함수 진입 직후

이 함수가 실제로 호출됐는지, 어떤 인자로 들어왔는지 확인한다.

[DBG] fn=open_file k=call args={path="a.txt" flags=0}

return 직전

early return이 많은 함수에서 어느 경로로 빠졌는지 남긴다.

[DBG] fn=open_file k=return value=-1 reason="not_found"

조건문 직전

조건문 안쪽보다 조건값 자체를 이름 붙여 남기면 분기 이유가 보인다.

[DBG] fn=open_file k=branch expr="file == NULL" value=1

반복과 계산 중간값

값이 조금씩 바뀌다가 어느 순간 깨지는 구간을 찾는다.

[DBG] fn=load_segment k=calc vals={read_bytes=400 zero_bytes=3696 page=0x3ff000}
04. 분석 예시

코드 흐름과 콘솔 로그를 같이 본다

로그만 보면 그냥 문자열 덩어리라서 감이 잘 안 온다. 그래서 코드가 어디를 지나고 있고, 그때 콘솔에는 뭐가 찍히는지 같이 놓고 본다.

로그 분석의 기본 질문은 세 가지다. 마지막으로 정상인 줄은 어디인가, 처음으로 이상해진 줄은 어디인가, 그 사이에서 어떤 값이 바뀌었는가.

05. Pintos 맥락

Pintos에서는 맥락도 같이 찍기

Pintos에서는 출력이 꽤 지저분하게 섞인다. 그래서 tid나 page table 같은 맥락을 같이 찍어두면 나중에 덜 헷갈린다.

Pintos에서는 kernel panic, page fault, interrupt context, thread context가 섞인다. 같은 함수가 여러 thread에서 호출되기도 하므로 로그에 최소한의 실행 맥락을 같이 남기는 편이 좋다.

예쁘게 만들자는 게 아니다. 나중에 fn=..., k=return, tid=... 같은 걸로 바로 찾을 수 있으면 충분하다.

06. 실제 사례

2026-05-12 fork-multiple

실제로 막혔던 로그를 넣었다. 처음부터 원인을 안다고 쓴 게 아니라, 어디부터 이상했는지 따라가던 기록에 가깝다.

이 사례는 Pintos VM 작업 중 fork-once는 통과하지만 fork-multiple에서 실패하던 상황을 로그로 좁힌 기록이다.

스포일러 주의

VM fork/copy/kill 쪽 얘기가 나온다. 원인 쪽은 접어뒀다.

성공 기준선fork-once는 child 하나를 만들고, child 종료 뒤 child SPT cleanup까지 끝난다.
실패 위치fork-multiple의 두 번째 child는 copy와 실행까지 끝나지만 cleanup 진입 직후 깨진다.
읽을 단서#GP, rax cccc..., vm_try_handl value=0, Kernel PANIC recursion을 같은 흐름에서 본다.

아래 두 로그는 발췌가 아니라 원본 파일 전체를 포함한다. 기본 상태에서는 문제 라인을 강조하지 않고, 토글을 켜면 fork-multiple 로그에서 단서 줄만 조용히 표시한다.

fork-once 전체 로그471 lines +
docs/daily/files/001/fork-once.output정상 기준선
fork-multiple 전체 로그661 lines +
docs/daily/files/001/fork-multiple.output실패 로그
읽을 단서+

바로 볼 수 있는 사실은 fork-once가 성공하고, fork-multiple의 첫 번째 child도 성공한다는 점이다. 두 번째 child 역시 copy와 child 실행까지는 끝난다.

깨지는 지점은 두 번째 child가 종료된 뒤 supplemental args={kill spt=0x80042520f0}에 들어간 직후다. 그 다음 Interrupt 0x0d, rax cccccccccccccccc, Kernel PANIC, vm_try_handl value=0, Interrupt 0x0e, Kernel PANIC recursion이 이어진다.

따라서 “fork 자체가 안 된다”가 아니라 반복 fork에서 cleanup 또는 소유권 문제가 터진다고 범위를 좁힌다.

원인 해설(스포일러)+

구현 관점의 결론은 copy와 kill 사이에서 공유되면 안 되는 자원, 특히 aux의 소유권과 해제 시점을 의심해야 한다는 것이었다.

당시 기록은 “부모와 자식이 같이 보는 공유 자원, 특히 parent 쪽 aux를 child가 같이 보고, destroy에서 free한 뒤 두 번째 child가 다시 접근하거나 free하려는 흐름”으로 정리했다.

이 사례에서 로그가 한 일은 정답을 출력한 것이 아니다. 실패가 같은 child와 cleanup 근처에서 나는지, 첫 번째 child와 두 번째 child의 차이가 무엇인지, copy와 kill 중 누가 공유 자원을 건드리는지를 묻게 만들었다.

07. 출력 원칙

나중에 찾을 수 있게만 찍기

내가 로그 찍을 때 대충 지키려고 한 규칙들이다. 거창한 로깅 시스템 말고, printf 로그가 덜 난장판이 되게 하는 정도다.

Pintos output에는 부팅 메시지, 테스트 메시지, panic 메시지가 섞인다. prefix와 event 종류를 고정하고, 제출 전 제거하거나 flag로 끌 수 있어야 한다.

grep 가능한 prefix

[DEG]처럼 고정 prefix를 붙이면 테스트 로그에서 내가 찍은 줄만 뽑아 보기 쉽다.

짧은 event 종류

k=call, k=branch, k=loop, k=return처럼 종류가 고정되면 실패할 때 보는 순서가 단순해진다.

자주 필요한 맥락

tid, 실행 문맥, address space 관련 값을 자동으로 붙이면 thread 로그가 섞인 상황을 분리할 수 있다.

켜고 끌 수 있는 장치

Pintos 테스트는 예상 output과 실제 output을 비교하므로, 디버깅 로그는 제출 전에 제거하거나 꺼야 한다.

08. 주의점

로그도 너무 믿지는 말기

로그도 부작용이 있다. 너무 많이 찍으면 읽기 싫고, 어떤 경우에는 로그 때문에 타이밍이 바뀔 수도 있다.

로그 출력은 공짜가 아니다. interrupt, scheduling, timing이 얽힌 코드에서는 로그를 찍는 행위 자체가 실행 순서를 바꿀 수 있다. 로그를 보고 버그가 사라졌다면 고쳤다고 단정하지 말고 관찰 때문에 타이밍이 바뀌었을 가능성을 생각해야 한다.

처음부터 모든 함수에 다 찍으면 로그가 너무 커진다. 넓은 범위에 적은 로그를 찍고, 이상한 구간을 찾고, 그 구간 안에 더 자세한 로그를 추가한 뒤, 원인이 좁혀지면 불필요한 로그를 지우는 식이 낫다.

최종 판단은 코드, 문서, 테스트 결과와 함께 해야 한다. 특히 Pintos에서는 reference 요구사항과 테스트가 중요하다.

형식이 흔들리면 검색도 흔들린다

here, AAAA, why? 같은 로그도 급할 때는 도움이 되지만, 시간이 지나면 어떤 함수에서 찍은 것인지 다시 추적해야 한다.

09. FAQ

자주 나오는 질문

나올 법한 질문만 짧게 넣었다. 길게 설명할 내용은 아니고, 발표 중간에 막히면 펼쳐보는 정도다.

왜 AI에게 바로 물어보면 안 되나요?+

안 되는 것은 아니다. 다만 로그 없이 물어보면 질문이 너무 넓다. 로그 분석이 끝난 질문은 원인 후보와 확인할 불변식까지 훨씬 구체적으로 묻는다.

그러면 로그만 쓰면 되나요?+

아니다. 로그, ASSERT, backtrace, GDB는 역할이 다르다. 로그는 실행 흐름과 값 변화를 시간순으로 보는 데 강하다.

실제 서비스에서는 이렇게 안 하나요?+

실제 서비스에서는 log level, request id, structured logging, aggregation, sampling 등을 쓴다. 여기서는 Pintos에서 시작하기 쉬운 printf 로그에 초점을 둔다.

로그를 제출 코드에 남겨도 되나요?+

Pintos에서는 조심해야 한다. 불필요한 debug output이 남으면 통과하던 테스트도 실패할 수 있으므로 제출 전에 제거하거나 꺼야 한다.

좋은 로그의 기준은 뭔가요?+

어떤 함수에 들어왔는지, 어떤 인자였는지, 어떤 조건이 true 또는 false였는지, 반복 중 어떤 값이 바뀌었는지, 어디서 어떤 값으로 반환했는지 답할 수 있으면 충분하다.

10. 마무리

결국 남겨둔 게 있어야 한다

결국 하고 싶은 말은 이거다. 로그가 대신 생각해주지는 않지만, 내가 생각할 재료는 남겨준다.

처음에는 원인을 모를 수 있다. 하지만 모르는 상태에서 바로 정답을 찾으려고 하면, AI에게 의존하거나 전체 코드를 무작정 읽게 된다.

로그를 남기면 질문이 “왜 터지지?”에서 “여기까지는 정상이고, 이 조건부터 이상하다”로 바뀐다. 그 차이가 크다.

그래서 Pintos에서 버그를 만나면 먼저 간단한 printf() 로그부터 남겨 보자. 함수 호출, 분기, 반복, 반환을 찍고, 마지막 정상 지점과 처음 이상한 지점을 찾자. 그 다음에 문서든, 팀원이든, AI든 물어보면 된다.
